# doc-to-md

### Key takeaways
- EXCEL, should we handle it? YES (XLSX/XLSM/XLSB/XLS/ODS, plus CSV), as a first-class format. Spreadsheets are the most PII-dense business files (HR lists, customer exports). Do not use a generic 'convert to Markdown, then run NER' path. Use a cell-aware path: read typed values with python-calamine; type each column (header keywords from the country pack, plus validator/regex voting over the column's values); give the same placeholder to the same value across the whole workbook; run NER only on free-text columns, with the header as context; render Markdown last.
- Excel defaults (data minimisation, GDPR Art. 5(1)(c)): read cached values, not formulas; always exclude veryHidden sheets; exclude hidden sheets, rows and columns by default, but print a notice ('2 hidden sheets skipped'), with include_hidden=true to opt in; comments and notes are opt-in; never output document properties, pivot caches, external-link caches, defined names, chart caches, VBA or custom XML; reject encrypted workbooks; cap cells per sheet and per workbook.
- Excel traps for our validators: Excel keeps only 15 significant digits, so a 16-digit card number stored as a number has its last digit replaced by 0 and fails Luhn. Leading zeros are lost (phone numbers, postal codes). Dates are serial numbers. IDs may be stored as text or as numbers. Merged cells leave holes. In columns whose header indicates a card, phone or NIR (French social security number), the checksum must therefore give way to header plus format. Large sheets make Markdown tables explode in token count, so offer a CSV-in-fence output and row limits.
- Returning an anonymised XLSX (writing values back with openpyxl) is NOT recommended for v1. Pivot caches, comments, metadata, external links and chart caches would carry the original PII into the returned file. The Markdown or CSV output contains only what we extract, which makes it safe by construction.
- General principle: the output Markdown contains only what the converters extract, so any part we drop cannot leak. The real risk is text that we capture but that detection misses: link targets (mailto:), image alt text, headers and footers, form-field values, email headers. The anonymiser must scan the whole Markdown, including URLs and alt text, after Unicode normalisation (zero-width characters and soft hyphens, PDF ligatures, line-end hyphenation).
- PDF fast path: pypdfium2 (Apache-2.0/BSD-3) is the fastest permissive text extractor (py-pdf benchmark: 0.1 s/doc at 95% quality, versus pypdf 3.2 s, pdfminer.six 5.3 s, pdfplumber 8.6 s). For structure on CPU, OpenDataLoader local mode (Apache-2.0, needs Java) scores overall 0.831 at 0.015 s/doc but is weak on tables (TEDS 0.489). Docling scores 0.882 at 0.762 s/doc with good tables (TEDS 0.887). All three figures are from opendataloader-bench on an Apple M4.
- Docling on x86 CPU (paper, 8 threads, AMD EPYC): 3.1 s/page on average (median 0.79). Layout model 633 ms/page, TableFormer 1.74 s/table, EasyOCR 13 s/page, docling-parse 81 ms/page. Turning OCR off saves 60%. Treat Docling as an opt-in 'quality' tier. It needs torch (the standard extra includes torch and torchvision), and releases come very fast (2.142.1), so pin the version.
- Exclude: PyMuPDF/pymupdf4llm (AGPL-3.0 or commercial). marker: its code is now Apache-2.0, but the weights use a modified OpenRAIL-M licence with a $5M threshold, and it depends on the OpenAI, Anthropic and Gemini SDKs. MinerU: custom licence requiring a commercial licence above 100M MAU or $20M monthly revenue, mandatory attribution for online services, automatic termination, and VLM/LLM dependencies. Also html2text (GPL-3.0+), extract-msg (GPL), and bundling pandoc (GPL-2.0+).
- MarkItDown (MIT, 0.1.9, 2026-10-21) is light but shallow. PDF scores 0.589 overall with 0 on headings (pdfminer/pdfplumber, no OCR). DOCX goes through mammoth, which drops headers, footers and comments. MSG reads only From, To, Subject and the plain body (no CC, HTML body or attachments). XLSX goes through pandas+openpyxl with no hidden-sheet filter and no comments. Borrow its per-format code; do not adopt it as the engine.
- DOCX via mammoth (BSD-2): it shows the document with tracked changes accepted (skips w:del and w:moveFrom, keeps w:ins and w:moveTo), includes footnotes, endnotes and text boxes, ignores comments by default, and does not read headers or footers. Images are inlined as base64 by default, so override convert_image. Complete it with python-docx 1.2 (MIT, comments support) for headers and footers.
- OCR stays opt-in on CPU. Tesseract about 0.5 s/page; OnnxTR (Apache-2.0, no torch) 0.57 s/page in fp32, 0.38 s in 8-bit, 0.15 s with OpenVINO (i7-14700K). EasyOCR costs about 13 s/page on x86 CPU, so avoid it. Detect pages without a text layer per page (few characters, large image coverage) and do not blindly drop invisible text (render mode 3): that invisible text is the OCR layer of scanned PDFs that were already made searchable.
- Security: PDF parsers are DoS-prone. pypdf has around 60+ advisories (about 10 in Sep-Oct 2026 alone), and pdfminer.six had an RCE through pickle CMaps (CVE-2025-64512, fixed in 20251107). Office files are ZIP+XML: openpyxl is unprotected against billion-laughs without defusedxml, and minidom (used by mammoth) depends on Expat 2.7.2 or later. Run every parse in a disposable, network-less subprocess with resource limits (nsjail or gVisor), check the ZIP before parsing, and enforce timeouts.

### Recommendations
- EXCEL pipeline (proposed v1). (1) Check magic bytes and the ZIP structure, reject encrypted files, cap sheets and cells. (2) python-calamine: list sheets_metadata, skip VeryHidden, skip Hidden unless include_hidden; read cached values with iter_rows. (3) Open openpyxl lazily only for hidden rows/columns, opt-in notes and hyperlinks. (4) Detect the header row, or use Excel table headers (load_tables). (5) Classify each column (header keywords from the country pack plus share of values passing validators). (6) Apply the same placeholder per value across the workbook. (7) Run NER only on free-text columns. (8) Render.
- Excel output format: '## Feuille: <name>', then a GFM pipe table when the sheet has at most about 2,000 cells; otherwise a ```csv fenced block (fewer tokens). Fill merged cells down and across so each row stands alone. Escape '|' as '\|' and turn newlines inside cells into spaces. Print typed dates as ISO 8601. Always finish with an explicit '[N rows / M hidden items omitted]' notice when anything was left out.
- Excel number handling: for numeric cells in columns whose header points to card, phone, NIR, SIRET or postal code, rebuild the string with Excel's number format (leading zeros) and accept a format/header match when the checksum fails, because 16+ digit numbers lose their last digits. Treat date-typed cells in birth-date columns as PII.
- CSV/TSV: decode with charset-normalizer (French Excel exports are often cp1252 with ';' separators), detect the delimiter with csv.Sniffer, then go through the same column-aware anonymiser as Excel. If CSV is ever returned, placeholders like [PERSONNE_1] carry no risk of formula injection.
- PDF: (1) pypdfium2 per page (subprocess pool). A page with fewer than about 30 characters and more than about 50% image coverage is a scanned page: OCR it if allowed (Tesseract or OnnxTR int8), otherwise report it. (2) Default to font-size heading heuristics. Use OpenDataLoader local or Docling (layout + TableFormer FAST, OCR off) as the opt-in 'quality=high' tier. (3) Add pypdf AcroForm values as a '## Champs de formulaire' list. (4) Annotations opt-in; attachments list names only; never output Info/XMP metadata.
- DOCX: mammoth with convert_image returning '[IMAGE: <alt>]', comments mapped only when include_comments, tracked changes shown accepted (the default), then markdownify. Add python-docx section headers and footers once, de-duplicated, under '## En-tête/Pied de page'. Never output core.xml, app.xml or custom.xml. Embedded OLE and xlsx: recurse only if opted in, with depth at most 1.
- PPTX: python-pptx walker modelled on MarkItDown: '## Diapositive N: <title>', text, tables as GFM, chart data as tables, alt text, '### Notes'. Hidden slides follow the same policy as hidden sheets. Drop comments and core properties.
- ODT/ODP: odfdo, excluding text:tracked-changes and office:annotation; ODS through calamine. RTF: striprtf. Legacy DOC and PPT: reject, or send to a sandboxed LibreOffice sidecar (opt-in). Never use pandoc, html2text or extract-msg.
- EML: stdlib email (policy.default). Output only From, To, Cc, Reply-To, Date and Subject, then text/plain, falling back to HTML through markdownify. Drop Received, Message-ID, X-Originating-IP, DKIM and similar headers (IPs and hostnames, minimisation). MSG: olefile or python-oxmsg with the same fields. Attachments: list their (anonymised) file names; recursive conversion only on opt-in, with limits on count, size and depth.
- HTML: remove script, style, iframe and meta; never fetch remote resources; markdownify; anonymise href and src (mailto:, URLs with names or emails). Use trafilatura only for URLs or web pages. Images: OCR opt-in, never output EXIF or GPS, otherwise reply that there is no text layer.
- Normalise before detection: NFC; remove zero-width characters and soft hyphens; expand ligatures (ﬁ, ﬂ); rejoin line-end hyphenation; collapse whitespace inside long digit runs in IBAN, NIR and phone candidates. Then anonymise the WHOLE Markdown, link targets and alt text included.
- Markdown conventions for LLMs: one '# <file title>' (the original file name may itself contain PII, so anonymise it); ATX headings that keep source levels; GFM pipe tables with a header row; footnotes as [^n]; page and slide boundaries as '<!-- page 3 -->'; no base64 images, no raw HTML except <br> if needed.
- Sandboxing: pre-forked worker pool with nsjail (no network, read-only filesystem, tmpfs) and limits RLIMIT_AS about 1-2 GB, RLIMIT_CPU about 60 s, RLIMIT_FSIZE 0 or small, RLIMIT_NOFILE about 64; wall-clock kill; recycle each worker after N documents; keep documents in memory, never on disk or in logs. resource.setrlimit is Unix-only, so Linux servers only.
- Up-front limits: upload at most 25-50 MB; PDF at most 300-500 pages; ZIP check (at most 1-2k members, total uncompressed at most 200 MB, per-member ratio at most 100:1, no absolute paths or '..'); XLSX at most about 1M cells; recursion depth at most 1; output at most N MB. Reject password-protected OOXML/PDF and macro-only files with typed errors.
- Dependency plan: the base install (permissive, no torch) is pypdfium2, pypdf, mammoth, python-docx, python-pptx, python-calamine, openpyxl, defusedxml, odfdo, striprtf, markdownify, charset-normalizer, olefile. Extras: [ocr] Tesseract or OnnxTR; [quality] docling-slim with torch CPU; [java] opendataloader-pdf. Pin every version and add a licence check in CI (e.g. pip-licenses) that fails on GPL, AGPL or SSPL.

### Risks
- Excel numbers: precision loss beyond 15 digits and stripped leading zeros make checksum validators miss real PII (cards, phones). Column-header context is mandatory, and a header-free sheet will under-detect.
- Excel with 'cached values only': files written by non-Excel tools (libraries, exports) may have formulas without cached results, so cells come out empty. Detect and warn; never evaluate formulas.
- Default exclusion of hidden sheets, rows and columns may surprise users ('where is my data?'). It needs a visible notice and an opt-in. Including them by default instead could send forgotten PII (a hidden HR sheet) to the LLM.
- Tables with names in a column without a meaningful header (e.g. 'Col B') get only weak NER on short strings, so recall drops. Consider value-level gazetteers (first names) across the column.
- PDF 'hidden text' filtering (OpenDataLoader) can wrongly drop the invisible OCR layer of searchable scans. White or zero-size text can carry PII or prompt injections. Pick one explicit policy and test it.
- Parser DoS and RCE: pypdf published about 10 DoS advisories in Sep-Oct 2026 alone; pdfminer.six had RCE through pickle (CVE-2025-64512). Without sandbox, timeouts and fast upgrades, one crafted file can take down a worker or worse.
- XML bombs and XXE in OOXML/ODF: openpyxl has no protection without defusedxml; mammoth's minidom depends on the bundled Expat version (2.7.2 or later is needed); MarkItDown unzips DOCX in memory without size checks. Check the ZIP before any converter runs.
- Licence drift: marker went from GPL to Apache for code but kept restricted weights; Kreuzberg went MIT, then Elastic-2.0 for some 4.9.x releases, then MIT as Xberg; OpenDataLoader went MPL to Apache; MinerU went AGPL to a custom licence. Re-check on every upgrade.
- Docling: very fast release cadence (2.142.x) and torch weight (hundreds of MB to GBs). CPU latency of seconds per page with tables, and OCR adds 5-13 s/page with EasyOCR. Not suitable as the default path.
- Training-data provenance: docling-layout-heron used proprietary IBM data, and docTR/OnnxTR weights do not document their training sets. The weight licences are permissive, but data provenance cannot be fully audited.
- Mammoth by default inlines images as base64 (output size, image PII) and drops headers and footers. python-docx may skip text inside w:ins (not verified). Different DOCX converters therefore produce different PII coverage, so cover both with regression tests.
- Returning an anonymised XLSX or DOCX later (writing values back) would carry hidden parts (pivot caches, comments, docProps, external links, custom XML) and is a major leak path if ever added.

### Open questions
- Excel defaults to confirm with the product owner: include hidden sheets, rows and columns by default, or exclude them with a notice (my proposal: exclude)? Include cell notes and threaded comments by default (my proposal: no)? Default output: GFM table or CSV fence above a size threshold?
- Is a structured Excel output (anonymised CSV or JSON per sheet) acceptable alongside Markdown, given constraint 5? Is returning an anonymised .xlsx explicitly out of scope?
- EdgeParse: upstream repo, maintainer and licence could not be verified (web search budget exhausted). Check it before any evaluation.
- Does python-docx's paragraph.text (and so Docling's DOCX backend) drop runs inside w:ins (inserted tracked changes), and how does it treat w:vanish hidden text? Needs a test corpus.
- Can openpyxl in read_only mode see hidden row/column flags (row_dimensions/column_dimensions)? If not, normal mode costs memory on large files and needs separate limits.
- Licence of the compressed-RTF decoders needed for MSG bodies stored only as RTF (compressed-rtf, RTFDE) was not verified. RapidOCR's MODEL_LICENSES.md returned 404.
- Is a JVM (OpenDataLoader) acceptable in the runtime image, given memory and cold-start costs, or should we stay pure Python plus native wheels with our own pypdfium2 heading heuristics?
- Build a French/EU benchmark corpus of real business documents (payslips, contracts, HR spreadsheets, scanned forms) to measure PII recall per converter. Public benchmarks measure layout fidelity, not PII coverage.

- MinerU's licence is Apache-2.0 plus conditions: a separate commercial licence above 100M MAU or USD 20M monthly revenue, mandatory prominent attribution for online services, automatic termination on breach. [https://github.com/opendatalab/MinerU/blob/master/LICENSE.md]
- On x86 CPU (AMD EPYC 7R13, 8 threads) Docling averages 3.1 s/page (Marker >16 s, MinerU 3.3 s, Unstructured 4.2 s); layout model 633 ms/page, TableFormer 1.74 s/table, EasyOCR 13 s/page. [https://arxiv.org/html/2501.17887]
- py-pdf benchmark: pypdfium2 5.14.0 0.1 s/doc at 95% quality; pypdf 3.2 s at 95%; pdfminer.six 5.3 s at 88%; pdfplumber 8.6 s at 74%; PyMuPDF 0.1 s at 94% (AGPL). [https://github.com/py-pdf/benchmarks]

- calamine read a 186MB, about 1M-row xlsx in 25.3 s (1.12M cells/s) versus openpyxl 238.6 s (117.6k cells/s), 9.43x faster. [https://github.com/tafia/calamine]
- python-calamine exposes SheetMetadata.visible (Visible/Hidden/VeryHidden), CalamineSheet.merged_cell_ranges (xlsx/xls only), to_python(nrows=...) and iter_rows. [https://raw.githubusercontent.com/dimastbk/python-calamine/master/python/python_calamine/_python_calamine.pyi]

- Excel keeps only 15 significant digits; digits past the 15th are set to zero (e.g. card numbers) unless the cell is formatted as text. [https://support.microsoft.com/topic/1bf7b935-36e1-4985-842f-5dfa51f85fe7]

- MarkItDown's XLSX converter calls pd.read_excel(sheet_name=None, engine='openpyxl') with no visibility filter, no comments and no size limits; its MSG converter reads only sender, To, Subject and PR_BODY via olefile. [https://github.com/microsoft/markitdown/blob/main/packages/markitdown/src/markitdown/converters/_xlsx_converter.py]

- [refuted] Extra (Excel trap takeaway): in card, phone or NIR columns, the checksum must give way to header plus format because digits are lost.
  - correction: Wrong for the NIR. It has exactly 15 digits (13 + 2-digit mod-97 key), within Excel's 15 significant digits, so a numeric NIR is stored exactly and its key still validates. The real trap is float-to-string conversion (e.g. 1.85057800608436E+14 or a trailing '.0'), so convert integral floats with int() before validating. SIRET (14) and SIREN (9) also fit. Phone numbers and postal codes only lose leading zeros and have no checksum. Only 16-19 digit card numbers lose digits, so the 'header plus format' fallback is needed only for cards. Corsican NIRs (2A/2B) are always text.

### Verifier notes
- WebSearch quota was exhausted on the first search, so every check above used WebFetch on primary sources (PyPI pages and JSON, GitHub raw files, HF cards, arXiv, Microsoft support, Python docs, lxml FAQ). EUR-Lex returned an empty page, so the GDPR Art. 5(1)(c) citation was not re-verified, though it is the standard data-minimisation provision.
- pdfminer.six: the security takeaway cites only CVE-2025-64512 (fixed in 20251107). A second pickle CMap issue, CVE-2025-70559 (GHSA-f83h-ghpp-7wcc, CVSS 7.8), says that fix was incomplete; it is patched only in 20251230. Pin pdfminer.six to at least 20251230 (latest 20260107). This also covers pdfplumber, which builds on it.
- Excel/NIR error: the takeaway lumps NIR with card numbers. The NIR is 15 digits, so Excel stores it exactly and the mod-97 key check still works; the real bug risk is float formatting (scientific notation or '.0'). SIRET (14 digits) is also safe. Only 16-19 digit card numbers lose digits. Phones and postal codes lose leading zeros but have no checksum. Rebuild the strings with int() plus the cell's number format (e.g. '00000', '0#########').
- Excel memory: openpyxl's own docs put full (non read-only) memory use at about 50 times the file size, so a 50 MB upload needs about 2.5 GB, above the proposed RLIMIT_AS of 1-2 GB. Pipeline step (3) (open openpyxl for hidden rows/columns, notes, hyperlinks) therefore needs a tighter size cap. Alternatively, stream the sheet XML with defusedxml/iterparse (<row hidden>, <col hidden>, comments*.xml, hyperlinks). python-calamine exposes no API for any of these; merged_cell_ranges covers xlsx/xls only, not xlsb or ods.
- Excel omissions: (1) sheet names, column headers, Excel table names and print headers/footers (headerFooter in the sheet XML) can carry PII, so the '## Feuille: <name>' heading must go through the anonymiser; (2) modern threaded comments (threadedComments.xml, author names in persons.xml) are separate from the legacy notes openpyxl reads; (3) calamine returns empty cells for formulas without cached values (e.g. files generated by libraries).
- CSV output: placeholders cannot cause formula injection, but un-anonymised cells starting with =, +, -, @, tab or CR still can. If CSV is ever returned, apply CSV-injection escaping to every cell.
- Licence-gate omissions: mail-parser[outlook] pulls extract-msg (GPL) and falls back to msgconvert (Perl). trafilatura's 'eval' extra pins html2text (GPL) and its 'all' extra adds faust-cchardet and pycurl. The pip-licenses CI gate must run on the resolved extras actually installed. Kreuzberg 4.9.x had Elastic-2.0 in its PyPI metadata; xberg 1.3.9 and kreuzberg 4.10.x are MIT.
- Stale benchmark versions: opendataloader-bench used opendataloader 2.2.1 (now 2.5.15), docling 2.84.0 (now 2.142.1) and markitdown 0.1.5 (now 0.1.9). OnnxTR figures are from v0.6.0 (now 0.9.0). The calamine benchmark used calamine 0.22.1 against openpyxl 3.0.10. The Docling paper's 13 s/page OCR cost is EasyOCR, but Docling's 'standard' extra now installs RapidOCR (onnxruntime). Re-measure on the target x86 hardware before fixing the thresholds.
- PyMuPDF 2.0 (2026-10-19) now contains the pymupdf4llm code (pymupdf4llm 2.0 is an empty shim). Still AGPL/commercial, so the exclusion stands, but name the packages correctly.
- OpenDataLoader: veraPDF components are redistributed under MPL-2.0 (elected from the dual licence), not GPL. JAXB (CDDL-1.1) and jaxb-impl (EDL-1.0) are also bundled. All acceptable, but notices are needed, and it requires Java 11+.
- Mammoth: w:fldSimple fields are dropped entirely (unrecognised element) and only mc:Fallback of AlternateContent is read. That is a text-loss risk, not a leak. Keep external_file_access off (the default); the README warns it performs no sanitisation of untrusted input.
- Maintenance flags: olefile last released 0.47 (2023-12), python-oxmsg 0.0.2 (2025-02), defusedxml stable 0.7.1 (2021, defusedxml.lxml deprecated), openpyxl 3.1.5 (2024-06), python-pptx 1.0.2 (2024-08). Consider vendoring or wrapping the MSG reader.
- Possibly missed tools: fastexcel (MIT, calamine plus Arrow, 0.21.0) for very large sheets with typed columns; LiteParse (Apache-2.0, now Rust/PDFium plus Tesseract) has predictions in opendataloader-bench and could be compared with pypdfium2/OpenDataLoader; docling-slim's models-onnxruntime extra might give a torch-free quality tier (unverified).
