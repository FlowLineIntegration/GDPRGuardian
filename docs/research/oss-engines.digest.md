# oss-engines

### Key takeaways
- Presidio is MIT, active and widely used (11.5k stars; four releases in 2026; latest 2.2.364 on 2026-07-22). In June 2026 it moved from Microsoft to the community-run data-privacy-stack org. The copyright line now reads 'Presidio Contributors', and containers now ship from ghcr.io/data-privacy-stack.
- Presidio has no France recognizers. The EU coverage it has: ES (NIF/NIE/passport), IT (5 IDs), PL PESEL, FI HETU, SE personnummer and organisation number, DE (9 IDs), UK (6 IDs), plus global IBAN, card, email, phone, IP, MAC, URL and crypto. Since 2.2.359 many country recognizers are off by default. Since 2.2.363 they can be filtered by country.
- spaCy is a mandatory dependency of presidio-analyzer 2.2.364, even with the new NoOpNlpEngine (2.2.364). The default config still loads en_core_web_lg, and the NLP artifacts are computed on every analyze() call. SlimSpacyNlpEngine (2.2.363) skips NER but still loads en_core_web_sm for tokens and lemmas.
- Presidio's context boost (LemmaContextAwareEnhancer) matches context words against lemmas from the NLP engine. It works on single words only, substring matching by default, 5 preceding hits, +0.35 boost. With NoOp, only context passed explicitly in the call is used. Each recognizer serves one language, so multilingual context means registering one recognizer per language.
- Presidio's analyzer only merges overlaps of the same entity type (remove_duplicates groups by entity_type). Overlaps between different types reach the anonymizer, which applies MERGE_SIMILAR_OR_CONTAINED (default) or REMOVE_INTERSECTIONS. Thresholds apply in order: per-entity, then per-recognizer (2.2.364), then the engine default of 0.
- Presidio's regex path runs one finditer pass over the full text for every pattern. Deny-lists are compiled into one regex alternation, which scales poorly for large gazetteers. The regex timeout defaults to 60 s.
- Presidio's GLiNERRecognizer uses urchade/gliner_multi_pii-v1 by default, threshold 0.30, ONNX optional, with character chunks of 250 and 50 overlap.
- Measured costs (third-party, not ours): regex alone 0.1 ms median vs Presidio+spaCy 15.1 ms on an M1 Pro. Presidio+spaCy lg about 40 ms per 1,000 chars vs GLiNER multi-PII 374 ms. Presidio 2.2.364+GLiNER: 255 ms median per short request, 59 s for 50K chars, 2.9 GiB RSS on 4 CPUs.
- Presidio has no built-in indexed placeholders or session mapping. Its InstanceCounterAnonymizer sample gives <PERSON_0>-style tags but is documented as not thread-safe. Batch deanonymization arrived only in 2.2.364. One benchmark found Presidio's redact-then-restore round trip exact on only 64% of documents, blamed on offset misalignment.
- LLM privacy layers mostly wrap Presidio and are thin or stale. LLM Guard was archived 2026-07-09 and pins presidio 2.2.358. Guardrails detect_pii is archived. LiteLLM calls external Presidio analyzer and anonymizer containers through PRESIDIO_ANALYZER_API_BASE and can restore masked values in answers (output_parse_pii). Lasso, NeMo, AISG and obot use Presidio plugins.
- A Presidio-compatible REST facade makes GDPR Guardian a drop-in backend for LiteLLM, the Lasso gateway, NeMo Guardrails and similar tools, without taking Presidio as a dependency.
- Closest prior art for the proxy and MCP modes: PrivAiTe (BSD-3) does numbered <TYPE_N> placeholders, an in-memory per-request mapping, and streaming restore including tool-call arguments, behind both an OpenAI-compatible and an Anthropic-native gateway. pseudonym-mcp (MIT) has [TAG:N] placeholders, session ids, 12 locale packs and FR_NIR with mod-97, but uses an Ollama LLM for names.
- French legal prior art is MIT and reusable as ideas. Cour de cassation's juritools pairs Flair NER with rules: IBAN checked with schwifty, Luhn for cards, French plate regex, and flashtext propagation of detected names to every occurrence. Its label tool links annotations so case variants get the same replacement. moteurNER reports F1 0.94 but publishes no code.
- Excel (the user's question): of the tools surveyed, only presidio-structured (MIT, 0.0.8, 2026-07-22) handles tables natively. It infers one entity type per column from an optional random sample of n rows (strategies: most_common, highest_confidence, mixed>0.5) and leaves columns with no hits untouched. The idea is cheap and reusable, but one type per column misses PII in free-text columns.

### Recommendations
- Build a custom lightweight engine with a Presidio-compatible recognizer interface rather than running on presidio-analyzer. Reasons: spaCy is a hard dependency; an NLP pass runs on every call (15-40 ms vs 0.1 ms for regex in third-party tests); the context boost needs lemmas; there are no FR recognizers; regex runs one pass per pattern; GLiNER chunking is 250-char. A large-vocabulary model like en_core_web_lg is unneeded for CPU-only, low-latency, regex-first detection.
- Mirror Presidio's contracts so the ecosystem keeps working. Keep RecognizerResult(entity_type, start, end, score, analysis_explanation) and EntityRecognizer.analyze(text, entities, nlp_artifacts). Keep the YAML recognizer schema (patterns, context, deny_list, supported_language) and extend it with country_code and score_thresholds. Ship a 'presidio' adapter as an optional extra that can load Presidio recognizers when installed.
- Expose Presidio-compatible REST endpoints (/analyze, /anonymize) next to MCP. LiteLLM's PII guardrail (PRESIDIO_ANALYZER_API_BASE), Lasso and NeMo-style gateways can then use GDPR Guardian as a drop-in backend.
- Vendor (with MIT attribution) Presidio's checksum validators: IBAN mod-97, Luhn, ES NIF/NIE, IT codice fiscale, DE Steuer-ID, PL PESEL, SE personnummer, FI HETU. Write the FR pack in-house (NIR mod-97 key incl. Corsica 2A/2B, SIREN/SIRET Luhn, plates per juritools), since neither Presidio nor any surveyed MCP covers SIREN/SIRET.
- Implement multi-word, multilingual context matching on a cheap tokenizer (casefold, accent-fold, light suffix stripping) instead of lemmas. Use Aho-Corasick for gazetteers and deny-lists (Presidio compiles them into a regex alternation). Group patterns per country pack to cut passes over the text.
- Run GLiNER or CamemBERT-size NER directly through ONNX Runtime: sentence-aware, token-based chunks near the model's max length, batched, with lazy load per language. Make NER optional per request so the regex-only path stays in single-digit milliseconds.
- Adopt juritools' propagation step: after detection, rescan the text for every surface form of each detected name (Aho-Corasick) so placeholders stay consistent and recall improves. Adopt LABEL's case-insensitive linking of variants.
- Placeholders and rehydration: build our own thread-safe session mapping (TTL, optional HMAC with an ephemeral key) instead of Presidio's non-thread-safe sample. Copy PrivAiTe's streaming restore across chunk boundaries and tool-call arguments. Test exact round-trips, since one benchmark saw Presidio fail on 36% of documents.
- Excel: of the tools surveyed, only presidio-structured handles tables. Copy its column-level inference: optional sample of n rows plus header names, with most_common/highest_confidence/mixed strategies, applied to the whole column with the session mapping. Run cell-level text analysis on free-text columns. Do not add presidio-structured as a dependency, since it pulls pandas and spaCy.
- Avoid as dependencies: LLM Guard and Guardrails detect_pii (archived), deduce and Textwash (GPL-3.0), anonymize-mcp models (CC BY-NC-SA), nvidia/gliner-pii (custom license, English-only), Presidio's LangExtract recognizer (LLM), the Ollama path in pseudonym-mcp (LLM), and presidio-image-redactor (out of scope).
- Run our own CPU benchmark (same hardware, FR/EN/DE texts of 1k/10k/50k chars) comparing the custom engine with Presidio's regex-only, NoOp+GLiNER-ONNX and slim configurations. All figures cited here are third-party, single-run or self-reported.

### Risks
- Presidio governance changed mid-2026 (Microsoft to the community data-privacy-stack org, new container registry, PyPI contact domain changed). Its long-term maintainer capacity is unproven. Mirroring its interfaces without depending on it limits exposure.
- Every performance figure cited is third-party, single-run or self-reported, and hardware and text lengths differ (redact's '32x Presidio', DataFog's 40 µs, the 255 ms/2.9 GiB GLiNER measurement). Decisions should rest on our own benchmark.
- Training-data provenance of PII encoder models: gliner_multi_pii-v1 (synthetic, apparently Mistral-generated), the Kiji model (LLM-synthesized) and OpenAI Privacy Filter (undisclosed). Weights are Apache-2.0, but LLM-generated data may carry upstream terms of service. Document this in the model register.
- Bundling spaCy French models brings LGPL-LR obligations. Download them at runtime or avoid them.
- One entity type per column (presidio-structured logic) under-detects PII in free-text Excel columns and in cells mixing several values.
- The MCP-server landscape is immature: most PII MCP servers have 0-4 stars, no license, cloud or LLM dependencies, or NC-licensed models. There is no mature prior art to fork; build in-house.
- Reversible pseudonymization keeps the data personal under GDPR. The mapping store, its TTL and the key must be designed as sensitive components (a legal point outside this scope).

### Open questions
- The shared WebSearch budget ran out mid-task. The official MCP registry, mcp.so and Smithery were not surveyed directly; MCP servers were found through glama.ai and GitHub only. A follow-up search pass is needed for completeness.
- Swiss and German court anonymization tools could not be identified or verified within the search budget.
- Where are MAPA's code and models published (ELG, Hugging Face, GitLab), and under what license?
- Kiji model base is inconsistent: the README says DistilBERT, the model card says deberta-v3-small+CRF. Its French quality on real (non-synthetic) text is unmeasured.
- Which LLM generated the synthetic training data of urchade/gliner_multi_pii-v1 and the Kiji dataset, and do its terms of service restrict downstream model use?
- Would upstream Presidio accept a French country pack (NIR, SIREN/SIRET)? Contributing it would give visibility while GDPR Guardian keeps its own engine.
- Excel output format: Markdown tables for large sheets vs returning an anonymized .xlsx or CSV. Constraint 5 (Markdown out) may not fit big spreadsheets; this needs a product decision.

### Verifier notes
- Web search quota for this turn ran out early, so all checks above use direct WebFetch of primary sources. PrivAiTe (BSD-3), pseudonym-mcp (MIT), moteurNER, Lasso/NeMo/AISG/obot claims and the anonymize-mcp CC BY-NC-SA claim were NOT verified.
- Excel (the user's actual question), correction to the takeaway: presidio-structured does not simply 'miss' PII in free-text columns. PandasDataProcessor replaces the ENTIRE cell value of any column mapped to an entity. A free-text column that gets a type (e.g. PERSON as most_common) is fully overwritten (over-redaction, utility lost). A column with no hit in the sample is left untouched (sparse PII missed). A mixed column (email+phone) gets one operator for all cells. Headers are not used, and the sample uses a fixed random_state=123. GDPR Guardian's design should run span-level detection per cell, with column inference only as a prior or boost.
- Excel omissions: the takeaways only look at cell values, but an .xlsx file (OOXML) also holds PII in comments and threaded comments (with author names), document properties (docProps/core.xml creator / lastModifiedBy), sheet names, headers/footers, hidden sheets, rows and columns, defined names, hyperlinks (mailto:), data-validation lists, cached values of formula cells, chart caches (strCache), pivot cache records (a full copy of the source data), external-link caches, and VBA in .xlsm. Anonymizing through pandas drops all of these silently or leaves them intact. Recommend openpyxl (MIT, 3.1.5, last release 2024-06-28) for in-place editing. Its docs warn that 'shapes will be lost from existing files if they are opened and saved with the same name'. Use python-calamine (MIT, 0.9.0) for fast read-only extraction. Also guard against CSV/formula injection when rehydrating values that start with = + - @.
- Omission: presidio-analyzer itself has BatchAnalyzerEngine (analyze_dict / analyze_iterator) for dict and tabular data, so 'only presidio-structured handles tables' is slightly overstated. presidio-structured's PandasAnalysisBuilder is built on it.
- Omission in the 'no built-in session mapping' takeaway: Presidio has reversible pseudonymization via the 'encrypt' operator and DeanonymizeEngine 'decrypt' (keyed), plus replace, redact, hash, mask, keep, custom and surrogate_ahds. There are no indexed placeholders or session store, but 'no reversible mode' would be wrong.
- France coverage nuance: Presidio's PhoneRecognizer defaults include region FR (DEFAULT_SUPPORTED_REGIONS US, GB, DE, FR, IL, IN, CA, BR), so French phone numbers are found, but only with English context words. CaSin and CaPostalCode recognizers declare language 'fr'. Still no NIR, SIREN, SIRET or FR plate.
- FR checksum pack: plain Luhn for SIRET is wrong for La Poste (SIREN 356000000 establishments use 'digit sum % 5 == 0', except the head office 35600000000048). NIR key: 97 - (first 13 digits mod 97), with 2A->19 and 2B->18. python-stdnum, the reference implementation, is LGPL-2.1, so implement from the spec and do not vendor it. Also consider the FR VAT key (FRkk + SIREN, kk = (12 + 3*(SIREN mod 97)) mod 97) and RIB key (alongside IBAN).
- Vendoring Presidio checksum validators: take them from >= 2.2.364. That release fixed FI HETU (illegal century separators, 29 Feb, case), ES NIF/NIE (lowercase, a validate_result exception), AU ABN, NG NIN and TH TNIN. 2.2.363 fixed PESEL and the German check digits. Older copies (e.g. LLM Guard's pinned 2.2.358) carry these bugs.
- Takeaway counts outdated or imprecise: main's default_recognizers.yaml has 13 DE recognizers (adds DeLanr, DeBsnr, DeVatId, DeFuehrerschein) versus the '9 IDs' in the docs. 2.2.364 also added PH_UMID, which is not on the supported-entities page.
- Context enhancer wording: '5 preceding hits' should read 'a window of the 5 preceding keyword lemmas (non-stopword tokens from nlp_artifacts.keywords), suffix window 0'. The boost is applied once: +0.35, at least 0.4, capped at 1.0. If nlp_artifacts is None, even explicit context is ignored.
- Benchmark caution: the 64% Presidio round-trip figure comes from the blogger's own redact/restore harness. Because the analyzer keeps cross-type overlapping spans (claim 7), naive replacement without the anonymizer's conflict resolution likely explains part of it. Do not present it as an intrinsic Presidio defect. The '40 ms vs 374 ms per 1,000 chars' figures have no traceable source.
- Model-license notes for an MIT project: fr_core_news_lg is LGPL-LR (optional download only). nvidia/gliner-pii uses the NVIDIA Open Model License and is English-only. fastino/gliner2-base-v1 is Apache-2.0 but tagged English-only. GLiNER multi PII weights and data are tagged Apache-2.0, but the base model's training set (urchade/pile-mistral-v0.1) has an empty card, so provenance is weak and should be noted in documentation.
- Missed candidate for CPU French NER: Dataiku Kiji's DataikuNLP/kiji-pii-model-onnx (Apache-2.0, ONNX, 26 PII types, trained on 6 languages including FR, DE, ES, NL, DA, EN, with a small deberta-v3-small/DistilBERT-class backbone). It was surveyed for its license but is absent from the NER recommendation, which names only GLiNER/CamemBERT. It is worth benchmarking next to gliner_multi_pii-v1 via ONNX Runtime.
- deduce license is inconsistent: GitHub says GPL-3.0, PyPI 3.0.6 says LGPL-3.0-or-later. 'Avoid' still stands.
- Legal angle not covered by this dimension but relevant to the Excel/session-mapping design: pseudonymised spreadsheets plus a mapping stay personal data for the mapping holder (GDPR Recital 26). The EDPB Guidelines 01/2025 on pseudonymisation went to public consultation (17 Jan to 14 Mar 2025). The final adoption status was not verified.
