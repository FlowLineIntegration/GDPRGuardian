# cpu-perf

### Key takeaways
- Encoder NER takes nearly all the CPU time. A regex, checksum and dictionary pass costs microseconds to milliseconds per 1k characters. Running a transformer over 1k characters costs roughly 0.2-1 vCPU-second. So the biggest throughput gain comes from gating: run NER only where the cheap pass finds signals, or where the caller policy asks for names, organisations or addresses.
- Rough throughput per vCPU (my estimate from the benchmarks cited, to be confirmed on our own hardware). (1) 6-layer encoder in ONNX Runtime int8 (DistilBERT, distilcamembert, GLiNER-small): about 1,000 tokens/s, i.e. about 3-5k characters/s. (2) 12-layer base model: about half that. (3) GLiNER-large: about 100-300 characters/s, too slow for CPU serving. (4) fp32: about half the int8 speed.
- ONNX Runtime 1.31.0 (MIT, 9 Oct 2026) is the right default CPU engine. Its docs recommend dynamic quantization for transformers, S8S8 QDQ as the first choice, and reduce_range only on CPUs without VNNI. Measured on Ice Lake: DistilBERT at sequence length 128 went from 56.3 ms to 27.3 ms in int8, keeping 99.7% of accuracy.
- For GLiNER, int8 is risky. The GLiNER docs say INT8 needs quantization-aware training to keep accuracy. One community GLiNER-small (DeBERTa-v3) build with dynamic INT8 weights and INT4 embeddings fell from 19/22 to 10/22 recall. Plan to ship fp32 ONNX (or OpenVINO bf16 on Xeons with AMX) and adopt int8 only after a French PII recall evaluation.
- GLiNER does not split long documents. The default max_len is 384 splitter tokens, and longer input is silently truncated to its prefix with only a Python warning. We must window the text ourselves (sentence-aligned, with overlap), remap offsets and merge spans. Presidio's GLiNER recognizer uses 250-character chunks with 50 characters of overlap and runs them one by one, which is a lot of per-call overhead.
- The ONNX Runtime Python run() releases the GIL. A single InferenceSession, holding one copy of the weights, can therefore be shared by several Python threads, each with its own inputs. This saves memory compared with one model per process. Session creation still holds the GIL. Uvicorn --workers starts processes with spawn, so the model is not shared copy-on-write and each worker pays its full memory.
- Do not create ONNX Runtime or PyTorch sessions before a fork. Locks and thread pools inherited by the child process cause hangs (gunicorn issue #2478). Only pure data such as gazetteers or automata built in C should be loaded before the fork, followed by gc.freeze(). Sessions belong in post_fork or in spawned workers.
- Multi-pattern regex speed (rebar, geometric mean, lower is better): Hyperscan 2.37, Rust regex 3.08, PCRE2-JIT 6.00, RE2 10.39, Python re 42.10, Python regex 43.26. Intel Hyperscan has been proprietary since 5.5. The python-hyperscan 0.9.1 wheels (MIT) statically bundle Vectorscan (BSD-3), including Linux ARM64 and Windows builds.
- Excel (the user's question): handle it, but through its own column-aware path rather than flattening the sheet to Markdown and running NER on every cell. Read with calamine, which is 9.4x faster than openpyxl (1.12M versus 118k cells/s). Classify columns from the header and sampled values, de-duplicate values, and run NER only on unique free-text cells in batches. Enforce cell and row limits. MarkItDown's path (pandas, openpyxl, HTML, then Markdown) is slow, includes hidden sheets and ignores comments.
- Rust has a measured but preliminary advantage on CPU: gline-rs ran 6.67 sequences/s against 1.61 for GLiNER.py on the same 8-core i9. Python glue code is therefore significant around GLiNER. Start with Python plus native libraries (ONNX Runtime, tokenizers, Vectorscan, ahocorasick_rs). Move pre/post-processing, span decoding and validators into a small PyO3 crate only when profiling shows Python taking more than about 20% of CPU.

### Recommendations
- Target architecture, per container: (1) async front-end (FastMCP stateless_http, REST and proxy on uvicorn) doing parsing and deterministic detection. (2) In-process deterministic engine: one Vectorscan database of all country-pack patterns as a prefilter, exact re-match with RE2, checksum validators (Luhn, mod-97, NIR key), ahocorasick_rs gazetteers and context-word windows. (3) NER executor: one ORT session per container shared by K threads (run() releases the GIL), intra_op_num_threads=1-2, K ≈ vCPU/intra. (4) Request-scoped placeholder mapping.
- Gate NER. Skip it when the caller policy needs only structured identifiers. Otherwise run it only on sentences that show signals: capitalised tokens not at sentence start, titles (M., Mme, Dr), name-gazetteer hits, address keywords, or @/phone context. Skip code blocks, JSON and numeric tables. Pass the cheap-pass spans to NER as known spans so the model does not redo them.
- Windowing for GLiNER: sentence-aligned windows of about 250-300 words, under 384 splitter tokens and 512 subwords, with 40-60 words of overlap. Remap to global character offsets. Merge same-label overlaps keeping the higher score, and let validated regex spans win for structured IDs. Batch windows of similar length (bucketing) in micro-batches of 4-16 with a 5-10 ms wait. Always pre-check length; never rely on GLiNER truncation.
- Model precision: for DeBERTa-based GLiNER, ship fp32 ORT with an offline-optimized graph first. Evaluate per-channel dynamic int8 (embeddings and attention kept fp32) and OpenVINO bf16 on AMX Xeons against a French/EU PII recall set; adopt only if recall drops by no more than 0.5 point. For BERT/CamemBERT-class NER, per-channel dynamic int8 (QDQ S8S8, no reduce_range on VNNI) is well-trodden: expect about 2-2.5x speed, about 2.5x smaller files, and roughly 1% lost spans.
- Keep the number of labels small: about 10-20 GLiNER labels per active country pack, because uni-encoder cost grows with prompt labels. If larger label sets are ever needed, consider the bi-encoder GLiNER with pre-computed label embeddings, subject to licence and provenance review.
- Threads and processes: avoid oversubscription (workers × intra_op threads must not exceed vCPUs). Disable SMT or pin threads where possible. Several small instances give near-linear throughput scaling, versus one instance using all cores. Keep ORT spinning on for latency and turn it off for density on shared nodes. Set OMP_NUM_THREADS=1 to stop libraries such as numpy oversubscribing.
- Fork safety and memory: never create ORT sessions before a fork. If gunicorn preload is used, preload only gazetteers and C automata, call gc.freeze(), and create sessions in post_fork. Cap the maximum sequence length, and consider disabling the CPU arena or running mimalloc, since the arena never shrinks. Measure memory with PSS. Budget roughly 0.5-0.8 GB per int8 GLiNER-multi session and 1.3-1.6 GB per fp32 session.
- Cold start: bake models into the image. Save the ORT-optimized model offline for the exact target hardware. Run warm-up passes at the batch sizes used, before the readiness probe passes (session creation holds the GIL). Scale horizontally on CPU utilisation with stateless pods.
- Python vs Rust: v1 in Python orchestrating native libraries. Profile with py-spy. If GLiNER pre/post-processing exceeds about 20% of CPU (gline-rs suggests the Python overhead is large), move tokenization glue, span enumeration and decoding, merging and validators into a PyO3/maturin crate, or reuse gline-rs ideas. Do not rewrite the HTTP or MCP layer.
- Excel, in direct answer to the user's question: accept xlsx/xls/xlsb/ods, but with a dedicated tabular pipeline. Read with python-calamine and enforce limits (e.g. max cells or rows, reject giant sparse ranges). Type each column from the header dictionary per language and a validator hit-rate on sampled values. Replace whole structured columns deterministically. De-duplicate values per column and run NER only on unique free-text cells in batches, with the column header prepended as context. Output a Markdown table per sheet, truncated or paginated for LLM context. Also scan sheet names, comments and document properties for PII.
- Throughput SLOs to plan with (estimates, to be validated): deterministic path ≥1 MB/s per vCPU of scanning, so request rate is bounded by HTTP/JSON framing. NER path about 3-5k characters/s per vCPU for 6-layer int8 encoders and about 1.5-2.5k for fp32 GLiNER-small. With gating on about 30% of the text, about 5-10k characters/s per vCPU overall. A 2k-character prompt costs about 0.2-0.7 vCPU-second at worst.

### Risks
- Silent PII leaks from GLiNER truncation: input longer than max_len is cut to its prefix with only a warning, both in the library and in Ray Serve.
- Int8 quantization of DeBERTa-v3 GLiNER can reduce recall a lot (19/22 down to 10/22 in one community test), turning a speed gain into missed PII. Always gate quantization behind a recall evaluation.
- Creating ORT or PyTorch sessions before a fork (gunicorn --preload) can deadlock workers. Uvicorn spawn workers each duplicate model memory.
- Thread oversubscription (processes × intra_op threads × numpy/OpenMP threads) collapses throughput and inflates p99 latency.
- The ORT CPU arena never returns memory. Variable-length inputs grow memory until the pod is OOM-killed unless lengths are capped or the arena is disabled.
- ReDoS: Python re and regex are backtracking. Any customer-defined or pack pattern run with re on untrusted text is a DoS vector. RE2, Vectorscan and Rust regex guarantee linear time but lack lookaround and backreferences, so patterns must be rewritten.
- Licence trap: Intel Hyperscan 5.5+ is proprietary. Make sure builds pull Vectorscan (python-hyperscan wheels bundle it).
- Presidio in the hot path brings per-call spaCy overhead, a slow phone recognizer, sequential chunk inference and, before PR #2280, quadratic de-duplication.
- Reversible pseudonymization across a session is hard with stateless horizontal scaling, because sticky sessions do not work reliably with MCP clients. Any shared mapping store adds GDPR exposure.
- Excel risks: zip bombs and huge sparse sheets. Hidden sheets, comments, sheet names and document properties can carry PII. pandas/openpyxl read cached formula values only, which may be empty in files written by non-Excel tools.
- onnxruntime-openvino lags core ORT (1.24.1 against 1.31.0). Free-threaded Python support in ORT is not mature (issue #26780). Do not depend on either yet.
- The benchmark numbers come from heterogeneous hardware and model sizes (vendor or community, some preliminary), so the per-vCPU estimates need confirmation on the actual EU host CPUs (Intel AMX vs AMD EPYC vs ARM).

### Open questions
- Which CPUs will run the EU hosting: Intel Xeon with AMX (where OpenVINO bf16 or int8 may win), AMD EPYC (ORT), or ARM Ampere/Graviton (ORT with dot-product int8, Vectorscan NEON)? Benchmarks must run on that hardware.
- How much recall does int8 (per-channel, embeddings kept fp32) cost for DeBERTa-v3/mDeBERTa GLiNER on French and EU PII? A labelled evaluation set is needed before any quantized model ships.
- Do ORT's transformer fusions (attention, LayerNorm) apply to DeBERTa-v2/v3 disentangled attention? The optimizer docs list tests on BERT, DistilBERT, RoBERTa and ALBERT only, so GLiNER may gain less from graph optimization.
- What does the traffic look like: mostly short chat turns, where per-request overhead and gating dominate, or long documents, where windowing and batching dominate? This sets the micro-batch policy and the latency SLO.
- Where does the reversible-pseudonymization mapping live across stateless replicas: a client-held sealed blob, or a server-side encrypted short-TTL store? What GDPR posture applies to each?
- Excel scope: values only, or also comments, sheet names, headers/footers, document properties and formulas? Is the output Markdown only, or must structure be preserved? What hard size limits apply (cells, rows, file MB)?
- Is the Python GLiNER pre/post-processing overhead on our workload as large as gline-rs suggests (about 4x)? Profile before committing to a PyO3 core.
- When will ORT ship stable free-threaded (3.14t) support? That would remove GIL contention in tokenization and post-processing for the shared-session thread model.

### Critical claims
- ONNX Runtime docs recommend dynamic quantization for RNN and transformer-based models. S8S8 with QDQ is the default first choice, and reduce-range is not needed on VNNI machines. [https://onnxruntime.ai/docs/performance/model-optimizations/quantization.html]
- ONNX Runtime 1.31.0 is the latest PyPI release (9 Oct 2026), MIT-licensed, and requires Python >=3.11. [https://pypi.org/project/onnxruntime/]
- The ORT Python binding releases the GIL in run() ('release GIL to allow multiple python threads to invoke Run() in parallel'). Session initialization does not release it. [https://github.com/microsoft/onnxruntime/issues/27063]
- GLiNER does not automatically split long documents into windows. config.max_len defaults to 384 splitter tokens, and over-limit input is truncated to a prefix with only a warning. [https://urchade.github.io/GLiNER/usage.html]
- GLiNER export_to_onnx(quantize=True) produces a best-effort dynamic INT8 model. The GLiNER docs state that models need quantization-aware training to keep accuracy at INT8. [https://urchade.github.io/GLiNER/convert_to_onnx.html]
- DistilBERT (Banking77, sequence length 128) on AWS c6i.xlarge: average latency 56.28 ms in ONNX fp32 versus 27.29 ms after int8 dynamic quantization, with accuracy 92.5% versus 92.24%. [https://www.philschmid.de/optimizing-transformers-with-optimum]
- gline-rs reached 6.67 sequences/s against 1.61 for Python GLiNER on CPU (gliner-multitask-large-v0.5, Intel Core i9 2.3 GHz, 8 cores/12 threads, 100 NuNER entries). [https://github.com/fbilhaut/gline-rs]
- A community GLiNER-small build with dynamic INT8/INT4 quantization ran in 236 ms but found 10/22 entities, against 375 ms and 19/22 for the fp16 build. [https://huggingface.co/Tazner/Gliner-small-edge-wo-int8-emb4]
- rebar search-time geometric means (lower is better): hyperscan 2.37, rust/regex 3.08, pcre2/jit 6.00, re2 10.39, python/re 42.10, python/regex 43.26. [https://github.com/BurntSushi/rebar]
- Intel moved Hyperscan to a proprietary license from 5.5. 5.4.2 was the last BSD release, and Vectorscan is the BSD fork. [https://www.phoronix.com/news/Intel-Hyperscan-Now-Proprietary]
- python-hyperscan 0.9.1 (8 Oct 2026) is MIT-licensed, statically bundles Vectorscan, and ships wheels for Linux x86-64/ARM64, macOS and Windows. [https://pypi.org/project/hyperscan/]
- Uvicorn's built-in multiprocess manager uses spawn rather than fork. The uvicorn.workers module is deprecated in favour of the uvicorn-worker package. [https://uvicorn.dev/deployment/]
- FastMCP multi-worker deployment requires stateless mode (stateless_http=True), and sticky sessions don't work reliably with MCP clients. [https://gofastmcp.com/deployment/http]
- On a 186 MB xlsx (28M cells), calamine took 25.278 s (1,122,279 cells/s) versus openpyxl at 238.554 s (117,612 cells/s), 9.43x faster. [https://github.com/tafia/calamine]
- Presidio's GLiNER recognizer defaults to character-based chunks of 250 characters with 50 characters of overlap. Chunks are processed sequentially without batching. [https://raw.githubusercontent.com/data-privacy-stack/presidio/main/presidio-analyzer/presidio_analyzer/chunkers/base_chunker.py]

### Verifier notes
- MAJOR (outdated): Both 'Session creation still holds the GIL' and 'warm-up before readiness (session creation holds the GIL)' are wrong for ONNX Runtime 1.31.0. Its pybind source releases the GIL around InferenceSession construction, Load() and initialize_session; 1.23.0 did not. Sessions can therefore be built in background threads. Separately, 1.31.0 now runs CPU weight prepacking in parallel on the intra-op pool, which shortens cold start. https://raw.githubusercontent.com/microsoft/onnxruntime/v1.31.0/onnxruntime/python/onnxruntime_pybind_state.cc
- MAJOR (technical error): 'per-channel dynamic int8 (QDQ S8S8, no reduce_range on VNNI)' mixes up two modes. ORT quantize_dynamic always produces U8S8 in QOperator/IntegerOps form, because activations are uint8 only. S8S8 QDQ is the default for quantize_static. Also, the ORT docs say per-channel on AVX2/AVX512 non-VNNI CPUs generally needs reduce_range as well.
- MAJOR (misattribution): The takeaway says the GLiNER-small build with 'dynamic INT8 weights and INT4 embeddings' fell from 19/22 to 10/22. In fact the Tazner weight-only block-wise INT8 MatMul + INT4 embeddings build kept 19/22, at 512 ms vs 375 ms for fp16 and 2.4x smaller. The 10/22 build was patronus-studio's dynamic int4/int8 edge build, which quantizes activations; DeBERTa-v3 attention outliers break it. So for GLiNER, weight-only INT8 (MatMulNBits-style, activations fp32) is a recall-safe way to save memory but not a speed-up, and dynamic activation int8 is the risky path. The recommendation should name this distinction.
- MAJOR (outdated framing): MCP spec revision 2026-07-28 (current) removed protocol-level sessions, Mcp-Session-Id, the initialize handshake, the GET stream and SSE resumability. Server-to-client requests now use MRTR, and the spec deprecates Sampling, Roots and Logging. FastMCP is at 4.1.3. Multi-worker deployment is naturally stateless for modern clients; stateless_http matters for legacy (2025-11-25 and earlier) clients. Any cross-call placeholder mapping, such as re-identifying placeholders in a later call, must use explicit server-minted handles passed as tool arguments, with GDPR implications for storing that mapping. https://modelcontextprotocol.io/specification/2026-07-28/changelog
- Inaccurate: 'the CPU arena never shrinks'. ORT has the run option memory.enable_memory_arena_shrinkage (e.g. 'cpu:0'), which needs the CPU arena enabled. The ORT docs also say mimalloc on Linux is only available via LD_PRELOAD.
- Inaccurate: the rebar numbers are labelled 'Multi-pattern regex speed'. They are geometric means of speed ratios over the whole curated set, and engines ran different numbers of benchmarks (hyperscan 28, rust/regex 38). The engine is Intel Hyperscan 5.4.2, not Vectorscan. Hyperscan reports all, including overlapping, matches by default, so the 'Vectorscan prefilter, then RE2 exact re-match' design is right but needs to say so.
- License nuance: the aho-corasick Rust crate is 'Unlicense OR MIT', not 'MIT OR Apache-2.0'. Vectorscan bundles BSD-2, BSL-1.0 and BSD-3 notices. uvicorn-worker metadata has a conflicting MIT classifier. All are MIT-compatible.
- Excel, calamine benchmark: it measures the Rust crate 0.22.1 (now 0.37.0) iterating rows with an empty loop body. python-calamine 0.9.0 (Requires-Python >=3.11) will show a smaller gap once cells are converted to Python objects, so measure it before quoting 9.4x. calamine's README says it does not read 'extra content'. Cell comments, threaded comments and docProps therefore need separate handling, for example zipfile plus defusedxml on xl/comments*.xml, xl/threadedComments, xl/persons and docProps/core.xml and app.xml, or openpyxl.
- Excel, omissions for GDPR completeness: pivot caches (pivotCacheRecords hold a full copy of the source data), hidden rows, columns and sheets, defined names, external links, chart caches, headers and footers, data-validation lists, embedded objects, VBA (xlsm) and cell hyperlinks can all carry PII. This matters especially if the output is ever a sanitized .xlsx rather than Markdown. Also add zip-bomb and XML-bomb limits (decompressed size, sharedStrings size), not only cell and row limits. MarkItDown 0.1.9 (MIT) is confirmed to use pd.read_excel(sheet_name=None, engine='openpyxl'), then to_html, then Markdown, with no visibility check and no comment handling.
- Omission: the knowledgator gliner-bi v2.0 models are English-only (language: en; Ettin and MiniLM/bge-en backbones). The bi-encoder fallback for large label sets would need a multilingual alternative or a French evaluation, beyond the licence and GPT-4o provenance review.
- Omission: ORT 1.31.0 fixed free-threaded Python wheel builds, and python-hyperscan ships 3.14t/3.15t wheels. Free-threaded CPython is an emerging option for the 'one session, K threads' design, since it removes GIL contention in pre- and post-processing. It is worth tracking against the PyO3 rewrite plan.
- Version updates: GLiNER is at 0.2.29 (8 Sep 2026; it added OpenVINO and ONNX export for span/token uni-encoders, and 0.2.28 added 'streaming inference'). gline-rs is at 1.0.0 (benchmark ran 0.9.0; Apache-2.0). OpenVINO is 2026.4.1, optimum-intel 2.2.0, uvicorn 0.54.0, fastmcp 4.1.3, regex 2026.9.29. The GLiNER usage docs state the truncation behaviour for 0.2.27; recheck it on 0.2.29.
- Performance caveats: the DistilBERT '2.48x' speed-up is a P95 ratio (mean ratio about 2.06x), and the source reports no file-size reduction. The gline-rs result used gliner-multitask-large, so the size of the Python overhead for GLiNER-small is unproven. The per-vCPU throughput figures (1k tokens/s, 3-5k chars/s, 100-300 chars/s for large) are the author's extrapolations and none of the sources state them. The c6i.xlarge figure used 4 vCPUs (2 physical cores) per call.
- Memory budget sanity check (supports the recommendation): onnx-community/gliner_multi_pii-v1 has fp32 model.onnx 1.16 GB, fp16 580 MB and int8 349 MB, consistent with about 1.3-1.6 GB per fp32 session and 0.5-0.8 GB per int8 session.
- Fork safety: gunicorn #2478 involves PyTorch (Stanza and sentence-transformers hanging with --preload), not ONNX Runtime. Extending the warning to ORT is a reasonable precaution but not documented in that issue.
- Method note: the web search budget ran out after the first query, so every check above used WebFetch on primary sources (PyPI JSON, crates.io API, GitHub raw sources and tags, HF API, official docs). The legal and GDPR angle was not assessed because none of the 36 claims is a legal claim.
