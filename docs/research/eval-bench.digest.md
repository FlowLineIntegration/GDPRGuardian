# eval-bench

### Key takeaways
- Excel (the user's question): yes, support it in v1, but through a separate tabular path with its own tests, not as plain text. Spreadsheets (HR, CRM, payroll exports) hold the most PII per byte, and the default xlsx→Markdown route (markitdown: pandas.read_excel + openpyxl, all sheets, no visibility check, comments ignored) loses cell types. That loss causes leaks.
- Leaks specific to Excel that the tests must cover: Excel keeps only 15 significant digits, so a 16-digit card number stored as a number loses its last digit and the Luhn check then rejects it. Phone numbers and postal codes stored as numbers lose their leading zero. An ID column with gaps turns into floats (1.85e+14), a partial leak. 'NA' is read as NaN. Formulas with no cached value come back empty.
- Better Excel detection works per column: a header-word list per country ('Nom', 'N° SS', 'IBAN', 'Date de naissance'), plus the share of each column's values that pass a validator, plus regex on every cell, and NER only on free-text columns. presidio-structured does not use column names at all (picks the most common entity type from values only), so GDPR Guardian can do better there.
- No French PII benchmark of real size is available under a usable license. Usable sources: FR-PII-Bench v0 (CC-BY-4.0, 300 docs, NIR/SIREN/SIRET with valid checksums), MAPA EUR-Lex fr (CC-BY-4.0, small), the gretel finance multilingual French subset (Apache-2.0, ~4.4k records, silver labels), Nemotron-PII (CC-BY-4.0, English) and TAB (MIT, English ECHR). Conclusion: build our own French synthetic generator plus a small private real-document holdout.
- License traps: ai4privacy 300k/400k are academic/non-commercial only. open-pii-masking-500k says CC-BY-4.0 in its YAML but its text imposes the Llama Community License. The older 43k/65k/200k cards show no license. Only openpii-1.5m (2026) is clearly CC-BY-4.0. CATIE-AQ/frenchNER is labelled CC-BY-4.0 but mixes in MultiNERD (NC-SA) and pii-masking-200k, so it inherits their restrictions. WikiNEuRal, MultiNERD, E3C, Meddies and the piimb benchmark are non-commercial.
- Lead with a metric that favours recall. Two precedents: presidio-evaluator's score function defaults to beta=2 (span IoU threshold 0.9), and the piimb leaderboard ranks systems by character-level masking F2. Add a TAB-style entity recall (an entity counts as masked only if all its mentions are), a document leak rate, an over-masking/FPR rate, and a false-mask rate on decoy values that look like PII.
- Faker fr_FR (MIT, 40.43.0) is only partly enough. ssn() computes the NIR key (97 − n mod 97, with 2A/2B handled) and siren()/siret() add a Luhn digit. But vat_id() is random (invalid key), the FR BBAN is random (invalid RIB key), NIR months are limited to 01-12 (no fictitious months 20-42/50-99, no NIA 7/8), and there is no La Poste SIRET exception. Custom generators are needed for these.
- Reference results to calibrate targets: the Cour de cassation Flair BiLSTM-CRF pseudonymisation engine reports micro F1 0.94 (address F1 0.865). The FR-PII-Bench author reports Presidio + French rules + spaCy fr_core_news_md at recall_any 0.728, finding 3% of street addresses. That figure is self-reported and the author tuned on the same set.
- Text obfuscation tests need a normalised shadow string (NFKC, remove zero-width and other invisible format characters including U+00AD and bidi controls, map lookalike characters with the UTS #39 v18.0.0 confusables data, Unicode License v3) with an offset map back to the original, so masking covers the original obfuscated characters. Measure partial leaks, not just entity hits.
- Tooling licenses are all fine for a dev/test toolchain: Hypothesis (MPL-2.0, test-only so no impact), python-stdnum (LGPL, use only as a comparison oracle in tests), pytest-benchmark 5.3.0 (BSD-2), asv 0.6.6 (BSD-3, 2026-06-27), pytest-codspeed 5.0.3 (MIT), nervaluate 1.2.1 (MIT), presidio-evaluator 0.3.2 (MIT, 2026-08-04; Presidio is now under data-privacy-stack, still MIT).
- Research limit: the shared web-search budget was used up before this agent's first query, so every fact here comes from direct WebFetch of primary pages (GitHub, Hugging Face, PyPI, MS Learn, unicode.org, cnil.fr). A few pages could not be checked (SWIFT IBAN registry 403, Quaero homepage refused, WikiNER figshare 403).

### Recommendations
- Excel decision for v1: support .xlsx/.xlsm/.ods/.csv in a 'tabular mode'. (1) Read typed cells yourself (calamine or openpyxl read_only), keeping the raw value and its number format, rather than pandas dtype inference. (2) Detect per column: header word list from the country pack, share of values passing validators, regex on every cell, NER only on free-text columns. (3) Mask cell by cell. (4) Output one Markdown table per sheet. (5) Cap the number of cells and rows. (6) List what is dropped (comments, headers/footers, document properties, images, macros) in the response.
- Excel test suite (generated with openpyxl): IDs stored as numbers versus text, 16-digit cards entered as numbers (truncated), phone numbers and postal codes that lost their leading zero, ID columns with gaps (float/scientific rendering), dates stored as serial numbers, 'NA' cells, hidden sheets/rows/columns, merged and multi-row headers, header not in row 1, mixed columns such as 'Commentaire' containing names, formulas without cached values. Metrics: cell-level recall and leak rate, column-level detection recall, cell-level false-mask rate.
- Build an in-repo eval package (dev extras only). One span schema {doc_id, text, spans[start,end,label,entity_id,identifier_type]}. Adapters for TAB, MAPA BIO, Nemotron, Gretel, FR-PII-Bench, refilled Judilibre and our synthetic data. A per-dataset label map to GDPR Guardian types. Our own character-level masking scorer, plus nervaluate, plus TAB-style all-mentions entity recall. JSON results plus a Markdown report, compared against a committed baseline.
- Dataset manifest: every external set is downloaded at evaluation time, pinned by revision and SHA-256, with its license and URL recorded. Never vendor NC, GFDL, CC-BY-SA, Llama-licensed or unclear data. Exclude ai4privacy 300k/400k/500k, CATIE-AQ/frenchNER, WikiNEuRal, MultiNERD, E3C, Meddies and the piimb aggregate.
- Main French corpus: our own template generator (10-50k docs: emails, meeting notes, contracts, HR records, support tickets, invoices, payslips, letters, prescriptions, Markdown tables) using Faker fr_FR plus custom ID generators (TVA key, RIB key, NIR fictitious months/NIA/97x/99, La Poste SIRET) and hard negatives (amounts, order and case numbers, 'article L. 1234-5', event dates). Keep a private holdout of 300+ real or consented French documents, annotated in LABEL, never used for tuning.
- Validator property tests (Hypothesis): every generated valid ID is accepted; any single-digit change is rejected; format() then clean() round-trips; separators and whitespace are invariant; agreement with python-stdnum as oracle on random inputs; fixed test vectors from python-stdnum doctests and official registries. Use derandomize=True and a stored example database in CI.
- Red-team mutation operators, applied to every gold span: spaces, dots, hyphens, slashes, NBSP U+00A0, narrow NBSP U+202F, thin space; irregular digit grouping; line breaks, soft hyphen and <br> inside IDs; full-width and mathematical digits; zero-width characters U+200B/C/D, U+2060, U+FEFF; bidi controls; Cyrillic/Greek lookalikes; OCR swaps O/0, l/1, S/5, rn/m; emails written as '[at]', '(at)', 'arobase', '&#64;', '%40'; uppercase 'NOM Prénom'; French-English code-switching; IDs split across Markdown table cells. Report recall per operator.
- Proposed v1 targets on the French synthetic set (red-team set in brackets). Checksummed IDs (NIR, SIREN/SIRET, IBAN, card): recall ≥0.995 [≥0.98], precision ≥0.98. Email, phone, IP, URL: recall ≥0.98 [≥0.95]. PERSON: recall ≥0.93, F2 ≥0.90. ADDRESS: recall ≥0.85. Document leak rate (any direct identifier fully visible) ≤1% synthetic, ≤3% holdout. Over-masking FPR ≤3% of non-PII characters. Decoy false-mask rate ≤5%. Holdout PERSON recall ≥0.90.
- Test placeholders and rehydration: the same entity gets the same [PERSONNE_n] across mentions in a document or session (consistency 100%); distinct entities never collide; anonymise then rehydrate gives back the exact input (100%, property-tested); placeholder spoofing (literal '[PERSONNE_1]' in input or in the LLM answer, unknown indices, modified brackets) is never rehydrated wrongly; masked Markdown keeps its structure (same number of headings, tables and rows).
- CI tiers. Per pull request (<10 min): unit, property and golden-file tests, the red-team suite, a 500-doc synthetic micro-eval with hard targets, and a no-regression gate (per-type recall drop ≤0.5 pt, any new leak in the golden set fails the build), plus pytest-benchmark or CodSpeed relative performance gates (≤10%). Nightly: full synthetic set, TAB, MAPA, Gretel-fr, Nemotron, refilled Judilibre, with bootstrap 95% confidence intervals, asv history and memray peak RSS.
- Performance protocol on reference CPU servers: chars/s per core; p50/p95/p99 latency for 1 KB, 10 KB and 1 MB Markdown, and for a 100k-cell workbook; cold start (model load); peak RSS with one NER model; throughput at 1/4/16 concurrent requests. Report the regex-only and regex+NER paths separately, and check that column sampling in tabular mode does not lower cell-level recall.

### Risks
- Inflated scores: synthetic, template-based and LLM-generated data use canonical formats and fluent text, so recall on real documents will be lower. Public PII NER models (GLiNER-PII variants) may have trained on ai4privacy, Gretel or urchade data, so scores on those test sets are inflated by contamination.
- Silver labels: Gretel's card admits false negatives and false positives in its LLM labels, so its precision figures are unreliable. Report it apart from gold sets (TAB, MAPA, FR-PII-Bench, our own data).
- License laundering on Hugging Face (CATIE-AQ aggregate tagged CC-BY, re-uploads of ai4privacy data with new tags), and NC datasets that could taint a hosted commercial service even when used only internally.
- Excel numeric coercion: 16-digit cards truncated to 15 significant digits fail Luhn and slip through as context-free numbers; phone numbers that lost the leading 0 escape French phone regexes; scientific notation leaks part of an ID; formulas without cached values hide values (pandas/openpyxl reads cached results).
- Behaviour of the default xlsx conversion: hidden sheets are included (safe but surprising); comments, headers/footers and document properties are dropped silently (lost utility, and if they are ever added, unscanned PII). Very large sheets can exhaust memory or latency budgets.
- Normalisation offset bugs: detecting on an NFKC/confusable-mapped copy and mapping spans back can leave obfuscated characters unmasked (a partial leak). This needs character-level leak tests.
- Rehydration abuse: an attacker or LLM output containing forged placeholders could pull in other entities' values, or mappings could leak across sessions.
- Noisy performance gates on shared CI runners give false alarms. Measure wall-clock on dedicated hardware or with instruction counting.
- Over-strict validators: rejecting NIR fictitious months (20-42, 50-99), NIA (7/8), Corsica 2A/2B or La Poste SIRETs turns real IDs into leaks.

### Open questions
- Will the EU-hosted service be commercial? If so, NC datasets cannot be used even for internal evaluation, and the ai4privacy openpii-1.5m provenance (generator undisclosed) needs a decision.
- Excel scope: must the output be Markdown only (per constraint 5), or will customers also expect an anonymised .xlsx/.csv round trip? Is a cell/row cap acceptable for v1, and should .xls/.xlsb be refused or converted?
- Which types count as direct identifiers with zero tolerance for leaks, and which as quasi-identifiers (dates, cities, job titles, ages) masked by policy? This drives the leak-rate targets and the TAB-style evaluation.
- Can we obtain a few hundred real or consented French documents and spreadsheets for a private holdout, and who annotates them (LABEL tool, two annotators, agreement score)?
- Could not verify (fetch blocked or web-search budget exhausted): SWIFT IBAN registry example vectors (HTTP 403), QUAERO homepage license text (connection refused; BigBio says GFDL 1.3), WikiNER figshare license (403), Judilibre licence page on courdecassation.fr (empty fetch; Licence Ouverte 2.0 confirmed only through the judilibre-search repo and a dataset card).
- EDPB Guidelines 01/2025 on pseudonymisation: the EDPB page showed only the v1 consultation (17 Jan-14 Mar 2025); final adoption status not confirmed.
- The NIR fictitious months (20-42, 50-99) come from French Wikipedia; an official INSEE specification should confirm them before validator rules are fixed.

### Verifier notes
- Research limit: the shared WebSearch budget was already used up (200 per turn) when I made my first search. Every verdict comes from direct WebFetch of primary pages (GitHub raw files, HF cards, PyPI JSON, MS Learn/Support, unicode.org, openpyxl/pandas/Hypothesis docs, cnil.fr, edpb.europa.eu).
- Outdated takeaway, Faker TVA: Faker fr_FR now has company_vat() in the company provider (changelog v37.12.0, 2025-10-07, 'Add french VAT number'). It computes a valid key: (12 + 3*(siren % 97)) % 97, equal to python-stdnum's int(siren+'12') % 97. Only the ssn provider's vat_id() is random. So no custom TVA generator is needed; use fake.company_vat(). Faker v40.23.0 (2026-06-10) also added Corsican 2A/2B codes to the NIR generator.
- Faker IBAN, precise state: the base iban() computes valid IBAN mod-97 check digits (98 - n mod 97). The FR BBAN is 23 random digits with no RIB key and no alphanumeric account numbers. So 'IBAN valid, RIB key invalid' is the accurate wording. Also confirmed: no La Poste SIRET exception (python-stdnum: SIRET starting with 356000000, except head office 35600000000048, needs digit sum % 5 == 0 instead of Luhn). NIR months are 1-12 only, and the sex digit is only 1 or 2. Besides fictitious months 20-42/50-99 and NIA 7/8, the NIR spec also allows first digits 3/4 and month 13 (fr.wikipedia, secondary source).
- Not verified: 'Presidio finds 3% of street addresses' does not appear on the FR-PII-Bench card. The card gives only aggregates: recall_any 0.728, precision 0.730, 921 false masks. It does confirm the set was used to tune the stop-list ('not a held-out test'). FR-PII-Bench draws names and addresses from Faker fr_FR, the same source GDPR Guardian plans to use. Scores on it and on a Faker-based in-house corpus will look better than real-world performance unless names and addresses also come from other sources (e.g. INSEE first-name files or BAN addresses; check their licenses).
- Not verified: the Cour de cassation Flair figures (micro F1 0.94, address F1 0.865). The pseudonymisation-api and juritools READMEs (both MIT) report no metrics. Cite a primary source before using these numbers as targets.
- MAPA: piimb/mapa-eur-lex-pii says only English is hand-annotated; French and the other 19 languages are LLM-projected. Use joelniklaus/mapa (manual, single annotator) for French gold. The French split is tiny: 1,297 / 97 / 490 sentences.
- Omission: ai4privacy pii-masking-openpii-1m (1,428,143 examples, CC-BY-4.0, (C) 2026 Ai Suisse SA, used by piimb) and openpii-1.5m both include French. They are missing from the 'usable sources' list and the nightly eval plan. Their labels are generic (SOCIALNUM, TAXNUM, IDCARDNUM; no NIR/SIREN). Neither card discloses the generating model, so keep the 'caution' verdict and pin the revision.
- CATIE-AQ/frenchNER_4entities also pulls in MultiCoNER v2 and WikiNER (no license on its HF card), not only MultiNERD and pii-masking-200k. The exclusion still stands.
- Excel recommendation (1) is partly infeasible as written. python-calamine 0.9.0 exposes typed values (int/float/str/bool/date/datetime/time/timedelta), sheet visibility (Visible/Hidden/VeryHidden) and merged_cell_ranges (xlsx/xls only). It has no number-format, comment or formula API and no hidden row/column information. openpyxl documents that comments are not supported with read_only=True. Keeping number formats and detecting hidden rows/columns therefore needs openpyxl in normal mode, or direct parsing of the sheet XML.
- Excel test-fixture pitfall: openpyxl writes a Python int with all its digits, so an openpyxl-generated '16-digit card stored as a number' is not truncated. To mimic real Excel (MS Support: digits past the 15th become zeros), write the already-truncated value (e.g. ...1110) or produce the fixtures with Excel or LibreOffice. The same applies to formulas without cached values: they only reproduce if the fixture comes from openpyxl, not from Excel.
- Security omission for tabular mode: openpyxl states that by default it 'does not guard against quadratic blowup or billion laughs xml attacks'; it recommends defusedxml (openpyxl 3.1.x, MIT/Expat). Add decompressed-size and zip-entry limits (zip-bomb guard) next to the cell and row caps.
- Format omissions: calamine also reads .xls and .xlsb. French Excel CSV exports usually use ';' as delimiter, cp1252/ANSI encoding (sometimes a UTF-8 BOM) and decimal commas. The CSV path and its tests should cover these. The pandas default NA list (pandas 3.1.0 docs) covers more than 'NA': also 'None', 'NULL', 'null', 'nan', 'N/A', 'n/a', '#N/A' and the empty string.
- Hypothesis: the built-in 'ci' profile (active when the CI env var is set) sets derandomize=True and database=None. The recommendation 'derandomize=True and a stored example database in CI' conflicts with that. Pin regression cases with @example or explicit test vectors rather than relying on the example database.
- memray is Linux/macOS only (PyPI description). The user works on Windows, so run peak-RSS profiling only in Linux CI, and use tracemalloc or psutil locally.
- Legal framing to add to reports: consistent [PERSONNE_n] placeholders with rehydration are pseudonymisation, not anonymisation. CNIL says pseudonymised data remain personal data and lists the three anonymisation criteria: singling out, linkability, inference. EDPB Guidelines 01/2025 on Pseudonymisation exist (public-consultation version, Jan-Mar 2025). Eval reports and README should not call the output 'anonymised'.
