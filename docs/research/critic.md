# critic

### Contradictions
- Presidio's role: oss-engines recommends a custom engine that only borrows Presidio's interface (because of spaCy, per-pattern regex passes and lemma-based context). ids-europe-west rates presidio-analyzer 'adopt' and says to use its recognizer and context machinery. ids-france rates it 'optional'.
- Excel column decision: licenses, ner-models, ids-france, ids-intl, name-address and cpu-perf say to label or mask the WHOLE column once it is classified. The oss-engines verifier, the mcp-arch verifier and eval-bench ('mask cell by cell') say to run span-level detection on every cell and use the column only as a prior.
- Column-classification threshold: tabular-excel uses a checksum hit rate of at least 0.6, ids-intl 70-80%, ids-france 80% or more, and presidio-structured's 'mixed' strategy more than 0.5. Nothing has been calibrated.
- Hidden content default: doc-to-md and tabular-excel exclude hidden sheets, rows and columns by default and add a notice. licenses says to anonymize hidden sheets, comments and metadata, or drop them with a warning. gdpr-legal says to strip or flag them. The tabular-excel verifier notes that autofilter- or outline-hidden rows also carry hidden=1, so an 'exclude hidden' policy would silently drop filtered data the user expects.
- Formulas: pseudo-ops says to 'evaluate or remove formulas before anonymising'. licenses says never evaluate them (pycel is GPL-3.0 and has CVE-2024-53924, formulas is EUPL). doc-to-md and tabular-excel say use cached values only and never output formulas. The name-address verifier says to rewrite them or replace them with values.
- Excel reader capabilities: eval-bench recommends keeping each cell's raw value and number format through 'calamine or openpyxl read_only'. Yet python-calamine has no number-format, comment or hidden-row API, and openpyxl read_only does not load comments (the licenses recommendation to use it for comments was refuted). mcp-arch proposes openpyxl for metadata checks, while doc-to-md's verifier warns that full-mode openpyxl uses about 50 times the file size in memory, beyond the proposed 1-2 GB RLIMIT.
- Excel output: tabular-excel, gdpr-legal and doc-to-md say Markdown only. doc-to-md switches to a CSV fence above about 2,000 cells, and tabular-excel switches to CSV for 'large tables'. mcp-arch says an anonymized .xlsx 'can wait', while doc-to-md says not recommended. tabular-excel says Markdown is 'clearly more accurate' than CSV; its verifier says Markdown and JSON are statistically tied, measured on a single small model.
- 15-digit Excel precision: doc-to-md, ids-europe-west and the name-address verifier say NIR- or IBAN-like numbers lose precision. Other verifiers show the NIR (15 digits), SIRET (14) and SIREN (9) are stored exactly, IBANs are never numeric, and only 16-19 digit cards and health-card numbers lose digits.
- Where the reversible mapping lives: mcp-arch proposes a server-side Valkey vault (AES-GCM, ephemeral key). gdpr-legal prefers the client holding it, or the server returning it encrypted and staying stateless. pseudo-ops allows memory-only storage or storage under a client-held session key. mcp-arch also proposes rehydration through an MCP App View that fetches originals, while pseudo-ops says never to offer rehydration via MCP, only through REST or the proxy.
- Session TTL: gdpr-legal says 24 h or less. pseudo-ops says about 30 min idle and about 12 h absolute. mcp-arch says only 'short TTL', and its verifier notes FastMCP session state has no TTL by default.
- Wording: gdpr-legal recommends the label 'désidentification : masquage des identifiants directs', but EDPB Guidelines 02/2026 para 40, cited by its own verifier, says not to use 'de-identified' while individuals remain identifiable.
- Anonymisation test: pseudo-ops and eval-bench cite the 'three CNIL criteria' (singling out, linkability, inference, from WP29 05/2014). gdpr-legal uses the EDPB 02/2026 criteria (no isolation, no linkage, no inference), currently in consultation until 30 Oct 2026.
- Digital Omnibus status: gdpr-legal says a Council mandate of 21 Oct 2026 keeps the current Art 4(1) definition and adds a pseudonymisation provision. pseudo-ops says a Council text of 2 Oct 2026 drops the relative definition and adds Art 25a, with Coreper meeting on 11 Oct. The dates and article details disagree, and neither was verified at the source. The EDPB 02/2026 adoption date is also given as both 7 and 8 July 2026.
- GLiNER label budget: ner-models recommends 4-8 labels (at most 4 in the fast tier). cpu-perf recommends 10-20 labels per active country pack.
- Quantization: ner-models' fast tier uses distilcamembert's shipped model_quantized.onnx, which is likely dynamic int8, against its own rule never to ship dynamic activation int8 without a recall test. cpu-perf describes 'per-channel dynamic int8 QDQ S8S8', which mixes two ORT modes. Verifiers say weight-only int8 saves memory but gives no speed-up.
- Training-data provenance: licenses says 'no LLM is involved at any stage', yet its default model gliner_multi_pii-v1 was trained on Mistral-generated data. ner-models grades Mistral- or E3-JSI-generated sets 'ok' but GPT-generated sets 'caution', with no stated policy.
- spaCy French models: ner-models lists fr_core_news_* as 'optional', while licenses and oss-engines say 'avoid' (LGPL-LR).
- python-stdnum: ids-europe-west, ids-intl and ids-north-east allow it as an optional runtime extra. licenses and ids-france keep it out of runtime and use it only as a dev oracle. Verifiers also show it gives false results as an oracle: IS kennitala, NO 2032 rule, LT codes starting with 9, BR IBAN registry v101, US ITIN ranges.
- schwifty: ids-france rates it 'optional', while licenses says to drop or isolate it because it pulls pycountry (LGPL-2.1-only).
- Company identifiers: ids-france says legal-person SIREN/SIRET are off by default. ids-north-east says to anonymize VAT numbers by default because sole traders' numbers are personal data. ids-intl leaves it as an open policy question.
- Placeholder labels: pseudo-ops proposes country-specific labels ([NIR_1], [SIRET_1]). ids-north-east recommends country-neutral labels ([ID_NATIONAL_1]) because a nationality-revealing label is itself a quasi-identifier.
- Steuer-ID strength: ids-europe-west puts it in the weak tier (about 1 in 10 random numbers pass). Its verifier shows about 1 in 270 pass with the exact official digit rule; the weak figure only holds under Presidio's looser rule.
- Context window size for gated identifiers: ids-france about 5 tokens, ids-europe-west about 50 characters, ids-north-east ±40 characters plus headers.
- Vectorscan/python-hyperscan platforms: name-address says Linux/manylinux only, while the verifier and cpu-perf show win_amd64, macOS and musllinux wheels in 0.9.1.
- Faker French VAT: ids-france says Faker's TVA keys are invalid and need a custom generator. The eval-bench verifier shows fake.company_vat() (since v37.12.0) computes valid keys; only ssn's vat_id() is random.
- Hidden-row handling covers xlsx only (streaming XML scan), yet v1 scope includes xls, xlsb and ods. For those formats calamine silently emits hidden rows and columns, so the stated 'exclude hidden by default' policy cannot hold for them.

## llm-file-channels: How spreadsheets actually reach LLM providers, and which channels GDPR Guardian can intercept
- why: The proxy design covers only text messages, tool results and tool-call arguments, and MCP covers only file references. In practice spreadsheets mostly reach LLMs in three ways. One is API file uploads: Files APIs, code-execution containers, base64 document blocks. Another is web-UI uploads on chatgpt.com, claude.ai and Le Chat. The third is Office add-ins: Copilot in Excel, Claude for Excel, Gemini in Sheets. Neither the proxy nor MCP sees the last two, and nobody researched the first. This decides whether Excel support is reachable at all in proxy mode, and whether a browser-extension or add-in surface is needed.
- prompt: Project context: GDPR Guardian is an MIT-licensed, EU-hosted, CPU-only, LLM-free anonymization service exposed as a REST API, an OpenAI/Anthropic-compatible LLM proxy (anonymizes requests, rehydrates responses) and an MCP server (FastMCP; tools take file references, never raw text). Today is 2026-10-24. Use primary vendor documentation, give dated URLs, verify current API status, and classify the license of any reusable code (ok: MIT/BSD/Apache; caution: LGPL/MPL; avoid: GPL/AGPL/proprietary). Research only, no files or shell. Research: (1) API file channels for each provider: OpenAI (Files API; Responses API input_file and the MIME types it supports, xlsx/csv included; code_interpreter container files; file_search), Anthropic (Files API; document content blocks; container_upload for the code execution tool; supported file types), Mistral (files, document OCR), Google Gemini (File API, inline_data) and Azure OpenAI. For each, state whether the file goes up in a separate request referenced by file_id, whether a transparent proxy can intercept and replace it (multipart parsing, keeping the file_id mapping consistent), and whether swapping the xlsx for an anonymized CSV or rebuilt xlsx keeps features such as code interpreter working. (2) Non-API channels: web-chat uploads (chatgpt.com, claude.ai, Le Chat, Gemini), Microsoft 365 Copilot in Excel, Anthropic 'Claude for Excel', Gemini in Google Sheets. Explain how enterprise GenAI-DLP products intercept them (Microsoft Purview endpoint/Edge DLP, Netskope, Zscaler, Harmonic Security, LayerX, Prompt Security, Nightfall browser plugin). Assess technical feasibility of an MIT browser extension under Manifest V3: can it intercept or replace file uploads and paste events? Assess an Office.js add-in: access to workbook data, its distribution and its limits. Name reusable OSS extensions and their licenses. (3) Microsoft Purview/MIP sensitivity-labelled and encrypted Office files: can they be read without the proprietary MIP SDK, are there published figures on how many enterprise files are encrypted, and what custom properties (MSIP_Label_*) leak tenant or site IDs. Deliver a matrix of channel versus surface that can intercept it (REST, proxy, local MCP, hosted MCP, browser extension, Office add-in), and recommend which surfaces v1 needs for Excel to be useful. List 5-15 critical_claims.

## spreadsheet-structure-column-typing: Table and header detection on messy real-world sheets, semantic column-type detection prior art, and a spreadsheet evaluation corpus
- why: Every dimension rests its Excel answer on column-level classification: header lexicon plus the hit rate of validators or gazetteers on sampled values, with thresholds that disagree (0.5, 0.6, 0.7-0.8, 0.8). Some dimensions then mask the whole column, others only use the column as a prior. All of this assumes tidy tables with one header row in row 1. Nobody checked how often real business sheets have multiple tables, multi-row or merged headers, key-value 'form' layouts or cross-tabs. Nobody surveyed column-type detection research or found a spreadsheet test corpus. If tidy tables are rare, the core detection design changes.
- prompt: Project context: GDPR Guardian is an MIT-licensed, CPU-only anonymizer with no LLM in its pipeline. Detection uses regex, checksum validators, gazetteers and small encoder NER models such as GLiNER or CamemBERT. It processes spreadsheets (via python-calamine) before they reach third-party LLMs, using per-country packs (FR first, then EU). The current plan types each column from header keywords plus the share of sampled values that pass validators, then applies the label to the column. Today is 2026-10-24. Give URLs for everything and verify the licenses of code, model weights AND training data. Research only, no files or shell. Research: (1) How common messy layouts are in real business spreadsheets: several tables per sheet, header not in row 1, multi-row or merged headers, transposed or key-value 'form' sheets (label in column A, value in column B), cross-tabs, notes and totals rows. Sources: the Enron spreadsheet corpus (Hermans & Murphy-Hill 2015), FUSE, VEnron, and studies on spreadsheet table detection (Microsoft TableSense, Docling's Excel backend, SpreadsheetLLM structural anchors, others). For each, give availability, license, and whether the algorithm is deterministic or a small encoder (allowed) versus an LLM (not allowed). (2) Semantic column-type detection: Sherlock, Sato, DoDuo, TURL, the GitTables and SOTAB benchmarks, and rule-based PII column classifiers (piicatcher, Capital One DataProfiler). Also how commercial classifiers combine column names with value sampling, and what thresholds or sample sizes they document: Microsoft Purview, Google Sensitive Data Protection, AWS Macie. For each, give license (code, weights, data), CPU cost and accuracy on PII-relevant types. Name reusable multilingual header lexicons (FR/DE/ES/IT/EN) under Etalab, CC0 or CC-BY. (3) Evaluation data: public spreadsheet corpora with real or realistic PII usable under an MIT-compatible license. Check the Enron spreadsheets' legal status and GDPR posture for testing. Assess xlsx files on data.gouv.fr as a structural (non-PII) corpus. (4) A concrete recommendation: column-as-prior versus whole-column masking versus per-cell detection; how to handle key-value form sheets and header detection; how to set thresholds with statistical confidence (sample size versus validator false-positive rate). List 5-15 critical_claims.

## excel-roundtrip-rehydration-formulas: Reversible pseudonymization for tabular outputs, operators that keep column types, and formula handling
- why: Rehydration was designed only for streamed text. Excel use cases with LLMs produce tables or files: code-interpreter xlsx or CSV, aggregated Markdown tables, rewritten formulas. Placeholders in those outputs get sorted, concatenated or split, and their types get coerced. Placeholders in numeric or date columns can also break the LLM's own pandas code. On formulas, the dimensions contradict each other: one says evaluate or remove them, one says never evaluate (pycel is GPL with a code-execution CVE), one says use cached values only. Formula-help and data-cleaning requests are among the most common Excel+LLM tasks, so this decides which Excel use cases v1 can support.
- prompt: Project context: GDPR Guardian is an MIT-licensed, EU-hosted, CPU-only, LLM-free pseudonymization service. Its default operator is a consistent indexed placeholder such as [PERSONNE_1], backed by an ephemeral per-request or per-session mapping (keyed HMAC internally). Rehydration of LLM answers happens only in the proxy or the REST client, never through an MCP tool. Spreadsheets are read with python-calamine (cached values) and returned as Markdown or, possibly, a clean rebuilt file. Today is 2026-10-24. Give URLs, verify licenses (ok: MIT/BSD/Apache; caution: LGPL/MPL/EUPL; avoid: GPL/AGPL). Research only, no files or shell. Research: (1) Deterministic Excel formula parsing and rewriting WITHOUT evaluation: the openpyxl Tokenizer, the 'formulas' package (EUPL; can its parser be used alone?), xlcalculator, pycel (GPL-3.0, CVE-2024-53924), and Rust options. How to find literal PII inside formula text (string constants, HYPERLINK, mailto) and replace it while keeping cell references, defined names and structured references. How cached values relate to formulas. Whether to emit anonymized formulas alongside values. (2) Rehydrating tabular and file outputs: do any existing tools (LLM Guard, PrivAiTe, Presidio batch deanonymize, LiteLLM output_parse_pii, Private AI, Protecto, Skyflow) rehydrate CSV, xlsx or JSON tables? Pitfalls: placeholders merged into longer strings, re-cased or split across cells; aggregates or counts computed over placeholders; CSV/formula injection when real values are written back; cell-type coercion. (3) Operators that keep column types so pandas or code-interpreter analysis still works: placeholders in numeric ID columns versus integer surrogate IDs; consistent date_shift on Excel serial dates (1900 and 1904 systems) across sheets; numeric bucketing; FF1 format-preserving encryption, which under NIST SP 800-38G Rev.1 2nd draft needs a domain of at least 10^6 and needs check digits recomputed. (4) Any 2024-2026 evidence on LLM table-QA or analysis accuracy with masked, surrogate and original identifier columns. Deliver a default operator table per column type for Excel, a rehydration design for tabular and file outputs, and a formula policy. List 5-15 critical_claims.
