# ids-europe-west

### Key takeaways
- Library status (verified 2026-10-24): presidio-analyzer 2.2.364 (MIT, 2026-07-22) now lives under the independent data-privacy-stack GitHub org. Docs are at presidio.dataprivacystack.org. python-stdnum 2.2 (LGPL-2.1+, 2026-01-04), django-localflavor 5.1 (BSD-3, 2026-08-01), Faker 40.43.0 (MIT).
- Presidio now covers a large part of this scope: DE (TAX_ID, TAX_NUMBER, SOCIAL_SECURITY, HEALTH_INSURANCE, ID_CARD, PASSPORT, FUEHRERSCHEIN, KFZ, HANDELSREGISTER, PLZ, VAT_ID, LANR, BSNR), UK (NHS, NINO, PASSPORT, DRIVING_LICENCE, POSTCODE, VEHICLE_REGISTRATION), ES (NIF, NIE, PASSPORT) and IT (FISCAL_CODE, VAT_CODE, IDENTITY_CARD, PASSPORT, DRIVER_LICENSE). It has nothing for AT, CH, LI, BE, NL, LU, IE, PT, GR, MT, CY, MC or AD.
- python-stdnum is the widest checksum oracle for this region: at.vnr/tin/uid, ch.ssn/uid/vat, li.peid, be.nn/bis/eid/vat, nl.bsn/btw/identiteitskaartnummer, lu.tva, ie.pps/vat, gb.nhs/utr/vat, es.dni/nie/nif/cif, pt.nif/cc, it.codicefiscale/iva, gr.amka/vat, mt.vat, cy.vat, mc.tva, ad.nrt. It is LGPL, so use it as a dependency or a CI oracle and never copy its code.
- None of the four libraries covers the strongly checked LU matricule (Luhn plus Verhoeff), PT NISS (only django-localflavor does), ES NSS (only Faker, as a generator) or the MT ID card. These need clean-room implementations from primary specs.
- Identifiers with a strong check (low false positives): CH AHV (756 prefix plus EAN-13), LU matricule, IT codice fiscale, ES DNI/NIE/CIF, BE NN/BIS, GB NINO (prefix rules), DE RVNR (VKVV weights), AT SVNR, IE PPSN, prefixed VAT numbers, IBAN, MRZ lines.
- Identifiers with a weak check (about 1 in 10 random numbers pass): NL BSN, PT NIF, GR AFM, DE Steuer-ID, GB NHS, IT P.IVA, DE KVNR. 9 to 11 digit numbers pass by chance, and with country='auto' one 9-digit number can be a valid BSN, NIF and AFM at the same time. These need context words or column headers.
- Identifiers with no check (context required): NL KvK, LI PEID/AHV (4-12 digits), PT SNS utente, DE/AT/CH/ES/IT/GR postcodes, most passports and driving licences, GB company number, plates. The AD NRT check letter and the DE Führerschein and UK driving-licence check characters are unpublished.
- The Eircode (IE) identifies a single address, so it is close to a direct identifier. Other postcodes are quasi-identifiers that are only worth masking inside an address context.
- Excel (the user's question): numeric-typed cells drop leading zeros. Examples: NL BSN 0xxxxxxxx, BE NN for 2000-2009 births, DE/ES/IT postcodes 0xxxx, GR AMKA. Excel also rounds numbers past 15 significant digits to zero (Microsoft), which irreversibly corrupts 20-digit health-card numbers. Normalise by expected length and use column headers as context.
- Presidio quality issues I found. (1) DE_ID_CARD and DE_PASSPORT treat character 9 as an ICAO check digit over characters 1-8, but the German document number is 9 characters with the check digit as a separate 10th MRZ character, so genuine numbers are likely rejected. (2) DE_TAX_ID accepts any digit up to 3 times, looser than the official rule. (3) Recognizers are bound to one language (DE ones run only on 'de' text).

### Recommendations
- Write GDPR Guardian's own MIT validators clean-room from primary specs: VKVV §2 (RVNR), ICAO 9303, HMRC NIM39110, IBZ RRN docs, ISO 7064, Luhn, Verhoeff, EAN-13. Run python-stdnum only in CI, as a differential-test oracle and optional extra, so its LGPL code never enters the repo.
- Use Presidio's recognizer and context machinery (MIT) or reimplement its interface. Pin the version, re-audit the DE recognizers, and register country packs separately from the document language, because a French document may contain a German Steuer-ID.
- Give each identifier a confidence tier. A: checksum plus fixed prefix or structure (AHV 756, VAT with country prefix, IBAN, MRZ, codice fiscale, DNI/NIE) is redacted without context. B: weak checksum (BSN, NIF, AFM, NHS, Steuer-ID, P.IVA) needs context within about 50 characters or a column header. C: no checksum (KvK, PEID, SNS, passports, postcodes) is redacted only with context.
- With country='auto', resolve collisions between 9-digit checksums (NL BSN, PT NIF, GR AFM, DE LANR) using context-word language and surrounding text, and emit a single placeholder per span.
- Excel (the user's question): process it. Read raw cell values (openpyxl), not displayed strings, and keep the number type in view. Re-pad numeric cells to the expected length when the column header names the identifier. Classify each column by the share of cells that validate, and mask the whole column when it is clearly an identifier column. Also scan sheet names, comments, headers and footers, defined names, hidden sheets and document properties (author).
- For Excel, flag numeric cells with more than 15 significant digits as potentially corrupted identifiers (health-card numbers, card numbers) and mask them conservatively. Never try to rebuild the lost digits.
- Ship small gazetteers for structural validation: DE Kfz district codes, CH and AT canton/district codes, IT Belfiore codes, ES province codes, IE county codes, GR/Latin homoglyph maps. Check each data source's licence (government open data such as Etalab, CC-BY or OGL is ok; ODbL should not be bundled).
- Use Faker only for structure and build valid-checksum generators for test corpora, because many Faker VAT and SSN outputs are invalid on purpose or by accident.
- Add one generic MRZ detector. It covers passports and ID cards for all 17 countries with a 7-3-1 check, and is cheaper and more precise than national passport regexes.

### Risks
- LGPL contamination: porting python-stdnum code (for example via an LLM-assisted rewrite) into the MIT repo would make those files LGPL. Re-implement from specs and keep provenance notes.
- False positives in numeric-heavy content (Excel financials, invoices). About 9-10% of random 9-11 digit numbers pass mod-11 or Luhn checks, so tier-B identifiers without context will over-redact amounts, phone numbers and order numbers.
- False negatives from Excel coercion: leading-zero loss (BSN, BE NN for 2000s births, AMKA, postcodes) and rounding past 15 digits silently break checksum validation.
- Presidio validator bugs, such as the DE ID card check digit and the loose IdNr rule, could cause silent misses or over-matching if adopted as-is. Its governance also changed in 2026 (Microsoft to the data-privacy-stack org), so monitor maintenance.
- Unpublished algorithms (DE Führerschein, UK DL check letters, AD NRT letter, IT CIE, PT SNS) limit precision. These identifiers need context and accept a residual FP/FN rate.
- Greek and Latin homoglyphs in the GR ID card, plates and AFM context can evade regexes unless text is normalised first.
- Identifiers that embed personal data (codice fiscale, RVNR, AT SVNR, BE NN, AMKA, CHI, UK DL) leak date of birth and sex even when partially masked, so the whole token must be replaced.
- Parts of this research were not verified: the web-search budget ran out mid-task, so the ES NSS variant, LU Verhoeff details, CY and MT secondary IDs, and the GR Personal Number structure rest on secondary sources.

### Open questions
- Liechtenstein: is the PEID the same as the LI AHV number (4-12 digits, no check)? Do LI residents also receive Swiss 756 AHVN13 numbers?
- ES NSS/NUSS: which control-digit variant does the TGSS specification use for numbers below 10^7? Faker's concatenation version or the province*10^7 + number version?
- Are the health-card numbers (IT tessera sanitaria TEAM 80380..., CH 80756... 20 digits, EHIC) ISO/IEC 7812 with a Luhn check? They exceed Excel's 15-digit precision.
- GR Personal Number (ΠΑ): what exactly are the 3 prefix characters, is there a check, and is the AFM embedded?
- DE Führerschein: confirm the real 11-character layout (e.g. specimen B072RRE2I55) against Presidio's regex (2 letters plus 8 digits plus 1).
- AT passport and ID card formats, IE and NL driving licence numbers, MT social security number, CY ID card and ARC formats, Monaco national and CCSS identifiers, Andorra CASS number: no primary source was retrieved.
- Data licences of gazetteers (KBA Unterscheidungszeichen list, ISTAT/Agenzia Entrate Belfiore codes, Eircode routing keys, Royal Mail PAF is proprietary, so do not bundle it).
- Should a column header alone (e.g. 'BSN', 'NIF') trigger masking of the whole column even when cells fail the checksum (typos, truncated Excel values)?

### Critical claims
- presidio-analyzer latest version is 2.2.364 (uploaded 2026-07-22), MIT-licensed, with the repository now at github.com/data-privacy-stack/presidio [https://pypi.org/pypi/presidio-analyzer/json]
- Presidio's supported entities now include DE_TAX_ID, DE_TAX_NUMBER, DE_PASSPORT, DE_ID_CARD, DE_SOCIAL_SECURITY, DE_HEALTH_INSURANCE, DE_KFZ, DE_HANDELSREGISTER, DE_PLZ, UK_DRIVING_LICENCE, UK_PASSPORT, UK_POSTCODE, UK_VEHICLE_REGISTRATION and ES_PASSPORT, in addition to UK_NHS, UK_NINO, ES_NIF, ES_NIE and the IT_* entities [https://presidio.dataprivacystack.org/supported_entities/]
- Presidio's DE_ID_CARD validator checks the 9th character as an ICAO 7-3-1 check digit over characters 1-8. de.wikipedia states the German document number is 9 characters and the check digit is a separate 10th MRZ character (e.g. T22000129 has check digit 3). [https://de.wikipedia.org/wiki/Ausweisnummer]
- python-stdnum 2.2 was released 2026-01-04 under LGPL v2 or later [https://pypi.org/pypi/python-stdnum/json]
- German IdNr: 11 digits, first digit not 0. Since 2016 one digit may appear three times among the first ten, but never three in a row. Check digit uses ISO/IEC 7064 MOD 11,10. [https://de.wikipedia.org/wiki/Steuerliche_Identifikationsnummer]
- German RVNR check digit (VKVV §2(6)): replace the letter by its 2-digit alphabet position, multiply by 2,1,2,5,7,1,2,1,2,1,2,1, sum the cross sums, take mod 10. Serial 00-49 male, 50-99 female or divers. [https://www.gesetze-im-internet.de/vkvv/__2.html]
- Austrian SVNR check digit: weights 3,7,9,(skip),5,8,4,2,1,6, sum mod 11. When the remainder is 10 the serial number is incremented, so such numbers are never issued. [https://de.wikipedia.org/wiki/Sozialversicherungsnummer]
- Belgian national number check = 97 - (first 9 digits mod 97). For people born from 2000 the digit 2 is prepended before the computation. [https://github.com/arthurdejong/python-stdnum/blob/master/stdnum/be/nn.py]
- Luxembourg national ID is 13 digits (YYYYMMDD plus 3-digit serial) protected by a Luhn check and a Verhoeff check [https://en.wikipedia.org/wiki/National_identification_number]
- Irish PPSN: since 2024, B is accepted as the second letter on new PPS numbers. Legacy W, T, X second letters are ignored by the check. [https://github.com/arthurdejong/python-stdnum/blob/master/stdnum/ie/pps.py]
- UK NINO: D, F, I, Q, U, V never used as first or second prefix letter. O is not used as the second letter. Prefixes BG, GB, KN, NK, NT, TN, ZZ are not used. Suffix is always A-D. [https://www.gov.uk/hmrc-internal-manuals/national-insurance-manual/nim39110]
- Excel keeps at most 15 significant digits. Digits after the 15th in longer numbers are changed to zero unless the cell is stored as text. [https://support.microsoft.com/topic/1bf7b935-36e1-4985-842f-5dfa51f85fe7]
- django-localflavor 5.1 (BSD-3-Clause) was released 2026-08-01. It has no packages for CY, LI, LU, MC or AD. [https://pypi.org/pypi/django-localflavor/json]
- Faker en_GB ssn() always generates NINOs with the reserved ZZ prefix and T suffix, so they never validate as real NINOs [https://github.com/joke2k/faker/blob/master/faker/providers/ssn/en_GB/__init__.py]
- Portuguese NISS check digit: weights 29,23,19,17,13,11,7,5,3,2 over the first 10 digits. Check = 9 - (sum mod 10). First digit is 1 or 2. [https://github.com/django/django-localflavor/blob/master/localflavor/pt/forms.py]

### Verification ({'confirmed': 60, 'refuted': 3, 'uncertain': 3})
- [refuted] 23. DE_ID_DOC: 9 chars (4-char authority code + 5 random), charset [CFGHJKLMNPRTVWXYZ] + digits (0 dropped since Nov 2021); old IDs T plus 8 digits; provisional 1 letter + 7 digits; check digit is separate 10th MRZ char; ICAO 7-3-1
  - correction: 'Old IDs: T plus 8 digits' is wrong. de.wikipedia says the serial on the old Personalausweis and Reisepass was digits only. T22000129 is the specimen number of the new card (T is in the allowed letter set), so it is not a legacy format, and Presidio's 'legacy' pattern T\d{8} rests on the same mistake. The rest is correct: 9 chars, digit 0 dropped since 1 Nov 2021, provisional documents 1 letter + 7 digits, check digit as the 10th MRZ char. Before 1 Nov 2023, numbers could in exceptional cases be letters only.
  - src: https://de.wikipedia.org/wiki/Ausweisnummer
- [refuted] 24. DE_FUEHRERSCHEIN: 11 alphanumeric chars (authority code, serial, check character, counter); check character not published
  - correction: The structure is right: a 4-char authority code, a 5-char alphanumeric serial (00000-ZZZZZ), a check digit and an Ausfertigungsziffer (1-9, then A...). But the check digit is documented. de.wikipedia, citing the Bundesdruckerei Kartenführerschein guide (p.24) and KBA Anlage 2, gives the method: A=10..Z=35, weights 9,8,...,1 over the first 9 chars, sum mod 11, remainder 10 -> 'X'. Example: B072RRE2I55 (sum 467 -> 5). Presidio's regex [A-Z]{2}\d{8}[A-Z0-9] does not even match this specimen.
  - src: https://de.wikipedia.org/wiki/Führerscheinnummer
- [uncertain] 40. LU_MATRICULE: digit 12 = Luhn over first 11; digit 13 = Verhoeff over first 11
  - correction: Wikipedia confirms the Luhn check over YYYYMMDDXXX but does not say which digits the Verhoeff check covers. No CTIE or other primary source could be fetched (web search budget was exhausted).
  - src: https://en.wikipedia.org/wiki/National_identification_number
- [refuted] 47. GB_DRIVING_LICENCE: 16 chars ... an arbitrary character, 2 check letters; check letters not published
  - correction: Characters 15-16 are 'two computer check digits which may be letters', so they can be digits or letters, not always letters. Character 14 is a digit (usually 9, decremented to separate duplicates). The photocard adds a 2-digit issue number, so 18 characters are printed. No public algorithm was found, which is consistent with 'not published'.
  - src: https://en.wikipedia.org/wiki/Driving_licence_in_the_United_Kingdom

### Verifier notes
- The web search budget for this turn was used up after the first query, so every check used WebFetch on primary or reference sources: PyPI JSON, GitHub raw source, gesetze-im-internet, gov.uk, Microsoft Support and Wikipedia. Claims 40 (which digits the LU Verhoeff check covers), 51 (ES NSS variant) and 60 (GR PA) are still uncertain for that reason.
- Presidio coverage is overstated for out-of-the-box use. In 2.2.364's conf/default_recognizers.yaml, all 13 DE recognizers (TaxId, TaxNumber, Passport, IdCard, SocialSecurity, HealthInsurance, Kfz, Handelsregister, Plz, Lanr, Bsnr, VatId, Fuehrerschein) are enabled: false. So are UK NINO, passport, driving licence, postcode, vehicle registration and ES passport. Only UK NHS, ES NIF/NIE and the five IT recognizers are on by default. DE_FUEHRERSCHEIN, DE_VAT_ID, DE_LANR and DE_BSNR exist in the code but are missing from the supported-entities docs page.
- Takeaway error: 'the DE Führerschein check characters are unpublished' is wrong. de.wikipedia (citing the Bundesdruckerei Kartenführerschein guide p.24 and KBA Anlage 2) documents the check digit: A=10..Z=35, weights 9..1 over the 4-char authority code plus the 5-char alphanumeric serial, sum mod 11, remainder 10 -> 'X'. Specimen: B072RRE2I55. Presidio's DE_FUEHRERSCHEIN regex \b[A-Z]{2}\d{8}[A-Z0-9]\b cannot match this specimen, so add it to the 'Presidio quality issues' list.
- The Presidio DE_ID_CARD/DE_PASSPORT issue is worse than stated. The regex requires the 9th char to be a digit, but the 5 random chars come from 26 alphanumerics (17 letters + digits 1-9), so roughly 65% of genuine numbers cannot match at all. Of the rest, the bogus 7-3-1 test over chars 1-8 rejects about 90%. Concrete failure: passport specimen C01X00T47 (MRZ C01X00T478) gives sum 531 -> 1, not 7, so it is rejected. Its 'legacy T\d{8}' pattern is also a misreading: T22000129 is the new card's specimen, and old (pre-2010) serials were digits only.
- Tier error: listing the DE Steuer-ID among 'weak check (about 1 in 10)' identifiers is wrong if the official digit-structure rule is enforced. Only about 3.7% of random 10-digit prefixes have exactly one digit twice or three times (never three in a row) and the rest at most once. Combined with MOD 11,10, about 1 in 270 random 11-digit numbers pass. It becomes weak only with Presidio's looser 'any digit up to 3 times' rule. GDPR Guardian should implement the exact rule and could raise the Steuer-ID to a stronger tier.
- License precision: python-stdnum's PyPI classifier says LGPLv2+, but COPYING is LGPL 2.1 and the file headers say '2.1 or later', so record it as LGPL-2.1-or-later. As an optional runtime dependency it is compatible with an MIT project. Bundling it into a frozen or standalone binary brings LGPL obligations (relinking/replacement), which supports the plan to keep it as a CI oracle or optional extra. openpyxl, proposed for Excel, is MIT (PyPI 3.1.5, 2024-06-28) and is fine.
- Excel recommendation omissions: (1) openpyxl preserves pivot tables in existing files, and the pivot cache (pivotCacheRecords) holds a full copy of the source data, so masking cells and saving can leave the original PII in the cache. Delete the caches or set refreshOnLoad, and scan them. (2) Chart XML holds cached series values (numCache/strCache). (3) Formulas: openpyxl returns formula text by default and cached values only with data_only=True, so scan both (literal PII inside formulas, cached results). (4) Also scan data-validation lists, threaded comments (their author identities), core.xml creator/lastModifiedBy, external-link caches and custom XML parts. (5) openpyxl warns that shapes are lost when a file is opened and saved. It cannot read legacy .xls, which needs a separate reader, and .xlsm VBA needs keep_vba. Decide whether output is a rewritten xlsx or a report.
- Excel nuance: the 15-digit truncation and leading-zero loss happen when Excel ingests the data (typing, or opening/importing a CSV). GDPR Guardian reading a raw CSV or the stored xlsx XML sees whatever was saved. So 'flag >15 significant digits' should target numeric cells of exactly 15 significant digits followed by zeros (e.g. 16-20 digit card or health numbers ending in 0s). Re-padding by column header is sound. Excel also turns some identifier-like strings into dates or scientific notation on CSV import, which is worth a detector.
- Minor corrections for implementers: (a) the AT Abgabenkontonummer and CY TIC position rules are 0-based, so state that explicitly; (b) localflavor's CH ID 'A-I only' restriction is an implementation artefact, since ICAO A=10..Z=35 is equivalent mod 10, so use ICAO values; (c) the UK driving-licence check chars (15-16) can be digits or letters, and the printed number has 18 chars with the issue number; (d) the BSNR has no public check digit and must not share the LANR validator; (e) stdnum's gb.utr strips K only as a prefix; (f) ES CIF letter/digit enforcement by entity type is not done by stdnum.
- Takeaway wording 'python-stdnum is the widest checksum oracle...' omits its DE modules (de.idnr, de.stnr, de.vat, de.handelsregisternummer), which are relevant oracles for the DE recognizers. stdnum has no es.nss (404) and no LU matricule (lu/ has only tva.py), consistent with the takeaway. django-localflavor mt/ has only a postcode field, so 'MT ID card uncovered' holds.
